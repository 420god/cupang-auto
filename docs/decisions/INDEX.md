# 결정

> **언제 읽나**: 기존 구조를 뒤집으려 할 때. "왜 이렇게 돼 있지?" 싶을 때. 코드에서 `D-NN`을 봤을 때.
> **최종 갱신**: 2026-08-21
> **관련 코드**: 각 항목의 "코드" 줄 참조

**ID를 붙이는 기준** — 넷 중 하나에 해당할 때만. 모든 것에 붙이면 목록이 소음이 된다.
1. 뒤집으면 비용이 큰 것  2. 이미 막다른 길로 판명난 것
3. 여러 문서·코드에서 반복 참조되는 것  4. 사업 규칙으로 합의한 것

나머지 "왜"는 주제 문서 본문에 있다.

### D-01 · 수집은 크롬 확장프로그램으로 한다

### D-02 · SKU 식별자를 쿠팡 발급 바코드로 한다
상태 확정(2026-08-18) · 관련 `domain/cost-model.md`, `api/couplus.md` · 코드 `db/migrations/015`, `web/js/50-purchase.js podPick()`

쿠팡 바코드 = 로켓그로스 입고용 = 쿠플러스 구매요청 입력값 = 구매대행 청구서에 찍혀 나오는 값.
**발주·청구서·창고·쿠팡이 전부 같은 번호를 쓰는 유일한 값**이라 조인키로 쓴다.
상품명 텍스트 매칭은 수백 개만 넘어도 반드시 깨진다.
**버린 것**: `KIT-CUSH-BLU-40` 같은 자체 SKU 코드 체계 — 이미 4곳을 잇는 값이 있는데 새로 만들 이유가 없다
**뒤집으려면**: 발주·청구서·창고·쿠팡 매칭을 전부 재작업해야 한다
채널 독립성을 위해 PK는 내부 uuid로 두고 바코드는 unique 자연키로만 쓴다.

### D-03 · 환율은 로트마다 저장한다
상태 확정(2026-08-18) · 관련 `api/couplus.md`

구매대행 환율과 작업비 환율이 **다르고**, 구매대행 환율은 **주문 생성 시각에 고정**된다
(320 → 310, 2026-08-05). 시스템이 "현재 환율" 하나만 들고 있으면 과거 로트가 전부 틀어진다.

### D-04 · 원가 소급 재계산 로직을 만들지 않는다
상태 확정(2026-08-18) · 관련 `domain/cost-model.md`

처음엔 "운임이 나중에 확정되니 과거 이익을 소급해야 한다"고 봤으나 **틀렸다** —
운임·통관이 환율에 포함돼 발주 시점에 원가가 사실상 확정되고, 뒤에 붙는 작업비는
**쿠팡센터 도착 전에** 청구서가 온다. 팔리기 시작할 땐 이미 원가가 확정돼 있다.
게다가 판매 이익을 미리 저장하지 않고 **볼 때마다 현재 로트 원가로 계산**하므로
소급이 자동으로 일어난다.

### D-05 · SKU 없이도 로트가 존재할 수 있다
상태 확정(2026-08-19) · 관련 `domain/cost-model.md` · 코드 `db/migrations/021`

**상품 등록 전에 먼저 발주하는 경우가 있다.** 물건의 존재와 상품 등록은 별개 사건인데
`sku_id not null`이 둘을 묶어놔서, 물건이 중국에 실재하는데 시스템엔 없었다.
SKU 없이 되는 것: 입고·불량·중국창고 재고 / SKU가 있어야 하는 것: 출고·판매원가·재발주 제안

### D-06 · 출고·작업비는 발주 단계가 아니라 별도 단위로 관리한다
상태 확정(2026-08-18) · 관련 `domain/inventory-flow.md`

부분 출고가 실제로 있고, 작업비 청구서가 여러 발주를 가로질러 묶인다.
그래서 "작업비 청구/쿠팡 출고중/쿠팡센터 도착"은 **발주 단위로는 참도 거짓도 아니다.**
발주 단계는 4개(청구서 수령·결제완료·중국배대지 배송중·중국배대지 도착)만 남긴다.

### D-07 · 보관비를 옵션에 배분하지 않는다
상태 확정(2026-08-17) · 관련 `domain/sales-profit.md`

보관비는 **그날 팔린 특정 주문에 안 묶이는 재고 전체 기준 고정비**다.
옵션에 배분하는 건 억지 정밀도였다. 날짜 합계 행에서만 실제값을 보여준다.

### D-08 · 반품의 상품별 귀속은 불가능하다 — 다시 시도하지 말 것
상태 **막다른 길**(2026-08-17) · 관련 `domain/sales-profit.md`, `api/wing-internal.md`

로켓그로스는 CS·반품을 쿠팡이 전담해서 **개별 반품 건을 보여주는 화면이 WING에 아예 없다**
(실제 API 캡처 90건에 반품 엔드포인트 전무).
**안분 배분도 검토했으나 채택 안 함** — 관련 없는 옵션에 비용을 억지로 배정하는 가짜 정밀도라
AI 분석 지향 원칙에 안 맞는다. 대신 대조 안내로 차액을 투명하게 보여준다.
**"해결해볼까" 하는 생각이 들면 이 항목부터 읽을 것.**

### D-09 · `product_items`(소싱 DB)를 실제 판매 데이터와 조인하지 않는다
상태 **막다른 길**(2026-08-16) · 관련 `domain/sourcing.md`

`product_items`는 **다른 판매자 상품을 조사한 목록**이라 실제 판매 옵션과 겹칠 이유가 없다.
이 조인을 두 번 시도해서 두 번 다 틀렸다(옵션ID 서브타이틀, 판매 원가).
전부 "—"로 뜨는 걸 "아직 소싱 안 해서"로 잘못 해석했었다.

### D-10 · 청구서 묶음은 위치가 아니라 산수로 복원한다
상태 확정(2026-08-19) · 관련 `domain/invoice-parsing.md`

배송비·총금액이 어느 줄에 찍히는지가 **매번 다르다**(첫 줄/한가운데/독립된 줄).
`총금액 − 배송비 = 그 묶음 줄들의 (수량 × 단가) 합`으로 끊으면 위치와 무관하고,
**맞아떨어지는 것 자체가 검산**이 된다. 세 번 연속으로 위치 가정에 실패한 끝에 나온 방법.

### D-11 · 취소 시 배송비는 남은 SKU들이 다시 나눠 진다
상태 확정(2026-08-19) · 관련 `domain/cost-model.md`

같은 판매자에게서 여러 옵션을 사면 배송비가 하나로 붙는데, 하나가 취소돼도 판매자는
나머지를 여전히 보내므로 **배송비는 그대로 나간다.** 그래서 환불은 상품가만 하고
남은 줄들의 개당 원가를 다시 계산한다. 취소는 출고·판매 전에 일어나므로 과거 이익이 안 흔들린다.

### D-12 · 취소해도 발주 수량은 줄이지 않는다

공급처별 취소 빈도를 보려면 원래 발주량이 남아야 한다. `qty_cancelled`로 따로 센다.

### D-13 · 예치금은 "예정 → 확정"으로 관리하고 최종값은 사람이 넣는다

### D-14 · 청구서 PDF 텍스트는 좌표 기반으로 추출한다
상태 확정(2026-08-19) · 관련 `domain/invoice-parsing.md`

`pdf-parse` 기본 추출기가 칸 사이 공백을 버려 파서가 통째로 오작동했다.
같은 PDF를 pypdf로 뽑으면 멀쩡했다 — **PDF엔 정보가 다 있었고 추출기만의 문제.**

한글은 한 단어가 여러 조각으로 쪼개져 와서 "계 란 비 슷"이 된다.

### D-15 · 문서를 두 층으로 나눈다 (자동 주입 vs 찾아 읽기)
상태 확정(2026-08-19) · 관련 `HOW-TO-DOCUMENT.md`, `rules/INDEX.md`

`CLAUDE.md`는 매 세션 자동 주입되는 **고를 수 없는 비용**인데 118,255자까지 자랐다

두려워지고, 두려우니 덧붙이게 되는 악순환이 있었다.

### D-16 · 웹은 Vercel, 쿠팡을 부르는 서버 일은 전부 VPS
상태 확정(2026-08-20) · 관련 `../ops/deployment.md`, `../api/coupang-open-api.md`

**고정 IP를 따로 사는 길은 이미 막다른 길로 판명났다.** 유료 프록시(Webshare)로
고정 IP를 사서 WING에 등록했더니 처음엔 200이 왔지만 곧 쿠팡 WAF가 HTML "Access denied"를
뱉었고, IP를 바꿔도 같았다 — 업체 IP 대역째 블랙리스트. **다시 시도하지 말 것.**

그래서 조각이 셋인 건 복잡해서가 아니라 외부 제약 때문이다:
쿠팡 Open API=IP 화이트리스트(→VPS) · WING 내부 API=로그인 세션(→확장프로그램) · 화면(→Vercel).
**Vercel을 없애 VPS로 합쳐도 확장프로그램은 못 없앤다** — 셋이 둘이 될 뿐이고,
대신 HTTPS 인증서·CDN·push 배포·롤백을 직접 하게 되며 **장애 격리를 잃는다**
(지금은 VPS가 죽어도 화면은 Supabase만 보고 뜬다).
**버린 것**: 전부 VPS로 통합 · Vercel Secure Compute(엔터프라이즈 전용) · 외부 고정 IP 프록시

쿠팡 쓰기(가격·판매상태 등)도 같은 이유로 VPS가 맡는다. 웹은 큐 테이블에 넣기만 하고
VPS가 Supabase Realtime으로 받아 실행한다 — 포트를 안 열어도 되고, 그 큐가 곧 변경 이력이 된다.

### D-17 · app.js를 모듈이 아니라 '순서 있는 일반 script'로 나눴다
상태 확정(2026-08-20) · 관련 `../../web/CLAUDE.md`

4,971줄 단일 파일이 커지고 있어 도메인별 10개로 쪼갰다(`web/js/00-core.js` … 마지막이 boot).
(2026-08-21: 등록 화면들이 86~94를 쓰게 되면서 `90-boot.js` → `95-boot.js` 로 이름만 옮겼다. 순서는 그대로 마지막이다.)
**ES 모듈로 안 간 이유**: 최상위 선언이 166개라 전부 `export`/`import`를 달아야 하는데,
얻는 건 스코프 격리뿐이고 "번들러·복잡한 과정 없이"라는 원칙과 부딪힌다.
순수 분할은 **이어붙이면 원본과 바이트 단위로 같아서** 동작이 바뀔 수가 없다(실제로 검증함).

**대가**: 전역 스코프를 그대로 공유하므로 **로드 순서가 곧 실행 순서다.**
자르기 전에 "로드 시점에 아직 정의 안 된 것을 참조하는 곳"이 0건임을 기계적으로 확인했고,
파일명 앞 숫자로 순서를 못 헷갈리게 했다. 순서가 어긋나면 에러가 아니라 **조용한 undefined**다.

### D-18 · 변경 이력은 항목(field)으로 정규화하고 봐야 할 지표를 행마다 박는다
상태 확정(2026-08-21) · 관련 `../domain/product-listing.md` · 코드 `db/migrations/026`

`sent_body`에 통짜 JSON을 남기는 것으로는 부족하다. AI에게 파헤치게 하면 매번 다르게
해석하고 결과가 흔들린다. 바꾼 항목을 `field`로 쪼개면 "썸네일을 바꾼 사례를 전부 모아
전후를 비교해줘"가 한 줄 SQL이 된다. 한 요청에서 둘을 바꾸면 두 행이 된다 —
섞인 변경은 원인을 못 가리므로 나중에 걸러내려면 쪼개져 있어야 한다.

`primary_metrics`를 행마다 두는 이유: 지표가 깔때기 단계별로 있어서 **바꾼 것에 따라
봐야 할 지표가 다르다.** 썸네일을 바꿨는데 전환율만 보면 아무 결론도 못 낸다.
가격 이력도 같은 표에 넣는다 — 분석 관점에서 가격과 썸네일은 같은 종류의 사건이고,
따로 두면 "가격도 내리고 썸네일도 바꾼 날"을 못 본다.
**뒤집으려면**: 이미 쌓인 이력의 의미가 바뀌어 과거 분석이 전부 무효가 된다

### D-19 · 신규 상품 등록은 기존 상품 복제를 기본으로 한다
상태 확정(2026-08-21) · 관련 `../domain/product-listing.md`, `../api/coupang-open-api.md`

최상위 23키 + 옵션 23키에 고시정보·필수속성까지 사람이 채우면 WING에서 하는 것과
다를 게 없다. 복제하면 배송·반품지·과세유형·고시정보·필수속성이 그대로 따라온다.
**다품종 소량이라 비슷한 상품이 계속 나오는 구조**에 맞는 선택이다.

규칙은 하나다 — **쿠팡이 발급하는 것은 지우고, 우리가 정하는 것은 남긴다.**
무엇을 지울지는 에러가 알려줬다("중복된 바코드가 존재합니다").
**버린 것**: 빈 양식으로 처음부터 입력(카테고리 메타 캐시는 만들어뒀으나 화면은 미구현)
**되돌릴 수 없음**: 등록은 실패해도 재시도하지 않는다 — 응답을 놓치면 두 번 등록된다

### D-20 · 지표는 엑셀이 아니라 WING 내부 API에서 직접 받는다
상태 확정(2026-08-21) · 관련 `../api/wing-internal.md`

사용자가 비즈니스 인사이트 엑셀을 주면서 시작했는데, 화면을 보니 **엑셀이 필요 없었다** —
그 화면이 이미 JSON을 받고 있고 엑셀은 그걸 포장한 결과다. 원본을 받으면 파일 다운로드도,
엑셀 파싱도, "모든 셀이 문자열"이라는 함정도 사라진다.

**버린 것**: 엑셀 업로드 화면 + 파서. 설계까지 했다가 화면 스크린샷을 보고 접었다
**주의**: 화면 주소(`/tenants/business-insight/...`)와 데이터 주소(`/tenants/rfm-ss/api/...`)가
다르다. 화면 주소를 API로 착각해 캡처가 0건이었다 — 경로를 추측하지 말고 전체 요청 목록에서 고른다


### D-21 · 등록은 "복제 뼈대 + 준비 표"로 나눈다 (모달 한 판을 폐기)
상태 확정(2026-08-21, 사용자 지시) · 관련 `../domain/product-listing.md` · `db/migrations/031`

D-19는 그대로다 — 복제는 계속 쓴다. 다만 **복제가 담당하는 범위를 뼈대로 좁힌다**:
배송·반품지·과세유형·필수속성·고시정보만 따라오고, **채우는 값은 전부
`listing_projects`(031)에서 온다.** 상품명을 고치려면 등록 화면이 아니라 상품명 화면에서
고치고, 등록 화면은 다 찼는지 보고 쏘기만 한다.

왜 바꿨나: 등록 모달 하나에서 다 받으면 **판단이 등록 직전 한 덩어리로 뭉친다.**
썸네일을 왜 그렇게 했는지와 가격을 왜 그렇게 정했는지가 한 칸에 섞이면 나중에
어느 쪽도 판정할 수 없다(D-18에서 이미 겪은 문제). 그리고 소싱에서 모은 데이터가
등록 화면까지 오는 길이 없어서, "이 기준으로 소싱 → 이렇게 만들어 등록 → 이렇게 수정 →
결과"가 한 줄로 안 이어졌다.

**payload(jsonb) 한 덩어리로 안 두는 이유**: `product_drafts`(030)는 보낼 몸통 스냅샷으로는
맞지만 준비 과정에는 안 맞는다 — "대표이미지가 아직 없는 것"을 물어볼 수가 없다.
준비는 컬럼, 보내기 직전 몸통은 jsonb로 나눈다.
**버린 것**: 상품수정 화면 안의 "새 상품 등록" 모달(옮긴 뒤 제거)
**옵션 단위로 갈리는 것은 둘뿐**(사용자 확인): 대표이미지 · 물류 입고 정보
