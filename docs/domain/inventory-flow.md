# 재고 흐름 — 발주 · 입고 · 출고

> **언제 읽나**: 수량이 안 맞을 때. 화면에 물량이 안 나올 때. 단계·상태를 고칠 때.
> **최종 검증**: 2026-08-19 (브라우저 시뮬레이션 — 부분 도착·부분 취소·되돌리기)
> **관련 코드**: `web/app.js` 발주/입고/출고 절 · `db/migrations/016,019,020,021,022`

## 실무 순서

```
구매요청(쿠플러스 웹)
  → 구매대행 청구서 PDF (카톡)        ← 원가 1차 확정
  → 입금                              ← [결제완료] 버튼
  → 1688 발주                         ← 여기서 "재고없음 취소"가 발생할 수 있다
  → 중국 배대지 창고 도착 (카톡 통보)  ← 입고 탭에서 도착 처리
  → 한국 입고요청 (카톡)
  → 작업비 청구서 (엑셀)              ← 원가 2차 확정
  → 쿠팡센터 납품
```

**중국 창고 재고는 쿠플러스 화면에서 볼 수 없다**(해당 탭 미사용). 우리가 직접 센다.

## 세 층으로 나뉜다 — 이게 핵심

| 층 | 단위 | 무엇을 표현 |
|---|---|---|
| **발주** (`purchase_orders`) | 청구서 1장 | 4단계: 청구서 수령 → 결제완료 → 중국배대지 배송중 → 중국배대지 도착 |
| **로트** (`inventory_lots`) | 발주 줄 1개 | 실제 수량. 도착·불량·취소·위치 |
| **출고** (`inbound_shipments`) | 한국행 1회 | **여러 발주를 가로질러** 묶인다 |

**왜 "작업비 청구 / 쿠팡 출고중 / 쿠팡센터 도착"이 발주 단계에 없나** → D-06
사용자가 처음 말한 순서엔 있었지만 두 가지가 드러나서 뺐다:
- **부분 출고가 실제로 있다** — 100개 중 60개만 보내고 40개는 창고에 남길 수 있다
- **작업비 청구서가 여러 발주를 가로질러 묶인다** — "28일 주문분 + 29일 주문분을 묶어서, 없는 건 빼고"

즉 그 세 단계는 **발주 단위로는 참도 거짓도 아니다.**

## 수량 계산

```
미도착   = qty_ordered − qty_arrived − qty_cancelled
중국창고 = qty_china    (도착 − 불량 − 출고분)
운송중   = qty_transit
쿠팡     = qty_coupang
```

**020 이전에는 로트를 만들 때 `qty_china`에 발주수량을 그대로 넣었다** — 아직 도착도 안 했는데
창고에 있는 것처럼 기록된 셈이라, 출고 화면이 "그 발주가 도착 단계인가"로 우회 판정을 해야 했다.
지금은 로트가 실제 도착 수량을 직접 갖는다.

## 진행 상태는 발주가 아니라 SKU 단위 — `lineProgress()`

한 발주 안에서도 어떤 SKU는 이미 쿠팡에 있고 어떤 건 아직 중국에 있을 수 있다.
**상태를 저장하지 않고 로트 수량에서 파생시킨다** — 저장된 상태와 실제 수량이 어긋날 일이 없다.

```
로트 없음            미연결
창고>0, 나머지 0     중국창고
운송중>0만           쿠팡 출고중
쿠팡>0만             쿠팡센터
두 곳 이상           일부 출고
전부 0               재고 없음
```

## 입고 — 물건의 물리적 상태

**도착은 SKU(로트) 단위다.** 1688에서 일부만 먼저 오는 일이 있어서 발주 단위로는 표현이 안 된다.
그 발주의 **모든 줄이 다 도착하면** 발주 단계가 자동으로 '중국배대지 도착'이 된다.

**도착 처리는 증분으로 쌓인다.**
```
51개 발주 → 48 도착 / 3 불량  →  창고 45, 미도착 3
          → 나머지 3 도착      →  창고 48, 대기 목록에서 사라짐 + 발주 단계 자동 전진
```

**불량 입력은 입고 탭으로 일원화했다**(발주 상세에서 제거) — 같은 걸 두 군데서 고칠 수 있으면
반드시 헷갈린다. 나중에 발견한 불량은 "중국창고 재고" 구역에서 뺀다.
**개당 원가는 절대 안 건드린다** — 불량분은 환불받거나 터는 것이지 남은 정상품 원가를 올리는 게 아니다.

**입고 화면은 로트만 보여준다** → 그래서 SKU 미연결 줄을 따로 경고한다(R-15).
청구서 줄에 SKU가 안 붙으면 로트가 아예 안 만들어져서 입고·출고·원가 어디에도 안 잡히는데,
화면엔 그냥 "없음"으로 보였다.

## 취소 → D-12

판매자가 못 팔겠다고 하는 경우. **발주 수량은 줄이지 않고** `qty_cancelled`로 따로 센다 —
"20개 발주했는데 20개 취소됨"과 "애초에 0개 발주"는 다른 사실이고, 공급처별 취소 빈도를
보려면 원래 발주량이 남아야 한다.

- **환불액은 추정만 하고 사람이 고친다** — 배송 전 취소면 배송비까지 돌아오지만 배송 후면
  판매자마다 다르다. 상품가만/배송비 포함 두 값을 참고로 보여준다. **기본값은 상품가만**
- **배송비는 남은 SKU들이 다시 나눠 진다** → `cost-model.md`
- **전량 취소면 발주 자체가 `cancelled`** — 모든 로트가 "도착 0 + 취소 = 발주수량"일 때만
- **되돌릴 수 있다** — 전량 취소해도 행을 목록에 남긴다(안 남기면 되돌릴 방법이 없다).
  되돌리면 환불 기록을 지우지 않고 `void`로 바꾼다

## 출고 — 원가가 확정되는 곳

**발주가 아니라 SKU 기준으로 모아서 보여준다** — 실무에서 "이 상품 보내주세요"라고 하지
"6월 26일 발주분 보내주세요"라고 하지 않는다.

```
[작업비 청구서 넣기]
  → 중국 창고 재고 목록 (전량이 기본, 수량 조절 가능)
  → 개당 작업비 확인·수정 (SKU 기본값 `work_fee_items`에서 자동)
  → 청구서 총액과 대조
  → 저장: 로트 분할 · 재고 중국→운송중 · 작업비 가산
  → [도착 처리]: 운송중→쿠팡 + arrived_coupang_at  ← 선입선출 정렬 기준
```

**총액을 안 넣어도 저장된다**(청구서 없이 출고하는 경로) — 그때는 `invoice_source='none'`.
**SKU 없는 물량은 출고 목록에서 빼되 요약에 수량을 표시한다** — 숨기면 "내 물건이 어디 갔지"가 된다.

## 예치금

발주 결제로 빠지고 취소·불량 환불로 들어온다. **가장 정확한 값은 결국 사용자가 넣는 것**이다 —
대행사가 잔액을 사진으로 알려주고 예치금은 그때그때 들어온다.

```
expected   시스템이 만든 환불 예정 (취소·불량)  → 금액 고치고 [확정]
confirmed  실제로 들어온 걸 확인함
void       취소를 되돌려서 무효
```

**계산 잔액(확정 입금·환불 − 차감)과 대행사 통보 잔액을 나란히 보여준다** — 둘이 다르면
어딘가 빠진 기록이 있다는 뜻이다.
`amount_krw`(사람이 인정한 금액)와 `estimated_amount_krw`(추정)를 나란히 남긴다(R-05).
