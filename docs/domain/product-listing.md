## 전체 그림

```
소싱 판단(예상치)  →  등록 초안  →  쿠팡 등록  →  수정(가격·이미지·검색어)
                                        ↓              ↓
                              coupang_item_metrics_daily (매일 지표)
                              product_change_history (무엇을 왜 바꿨나)
                                        ↓
                              v_product_experiments (전후 비교)
```

**핵심은 "바꾼 것"과 "그 결과"를 잇는 것이다.** 그러려면 둘 다 남아 있어야 하는데,
2026-08-20까지는 둘 다 없었다 — 상품 정보는 바꾸면 덮어썼고 노출·클릭 지표는
어느 표에도 없었다.

## 왜 큐를 거치나

**웹은 쿠팡을 직접 못 부른다**(IP 화이트리스트, D-16). 웹은 `coupang_write_queue`에
"무엇을 해달라"만 넣고, 고정 IP를 가진 VPS 워커가 2초마다 집어서 실제로 쏜다.

그래서 **워커가 죽어 있으면 웹에서 아무리 눌러도 큐에 쌓이기만 한다.** 화면이
"요청됨"만 보여주면 사람은 영원히 기다리게 되므로, 2분 넘게 처리 안 된 요청이 있으면
화면이 워커를 의심하라고 말한다.

| 큐 종류 | 하는 일 |
|---|---|
| `price` | 판매가 변경 |
| `price_sync` | 가격·재고·판매여부 재조회 (대상 없으면 전체) |
| `product_fetch` | 상품 원문을 가져와 registry에 보관 |
| `product_update` | 상품명·검색어·대표이미지·상세페이지 수정 |
| `product_create` | 신규 등록 (복제 기반) |
| `category_meta` | 카테고리 필수속성·고시정보 캐시 (빈 양식 등록용, 아직 미사용) |
| `sale_stop`/`sale_resume` | **미검증이라 워커가 거부한다** |

## 수정은 전체를 되보낸다

쿠팡 상품 수정은 **부분 수정이 안 된다.** 그래서 워커가 **쏘기 직전에 쿠팡에서 최신
상품을 조회해** 거기에 변경분을 얹어 보낸다. 우리 DB의 사본을 보내면 그 사이 WING에서
바뀐 게 통째로 덮인다 — 빠뜨린 필드는 지워지기 때문에 특히 위험하다.

보낸 몸통은 `sent_body`에 통째로 남긴다. 전체 PUT이라 **무엇을 덮어썼는지가 사고 조사의
전부**가 된다.

## 등록 파이프라인 — 소싱한 상품에 데이터를 쌓아 올린다 (2026-08-21 재편, D-21)

**아래 "등록은 복제가 기본이다" 절은 여전히 맞다. 다만 복제의 범위가 뼈대로 좁아졌다.**

```
소싱 즐겨찾기 → [등록 준비] → listing_projects 1건 + 옵션 1행
   ├ 뼈대        복제 원본 또는 listing_templates  (배송·반품지·과세·필수속성·고시정보)
   ├ 카테고리    display_category_code
   ├ 상품명·검색어
   ├ 대표이미지  listing_assets(kind='rep')     ← 옵션별
   ├ 상세페이지  listing_assets(kind='detail')  ← 상품 단위
   ├ 물류·바코드 listing_project_items          ← 옵션별
   └ 가격        listing_project_items
              ↓ 다 찼으면 (v_listing_ready.all_done)
   상품등록 화면에서 payload 빌드 → coupang_write_queue(product_create)
```

**등록 화면은 값을 받지 않는다.** 상품명을 고치려면 상품명 화면에서 고친다. 이유는
등록 직전에 한꺼번에 받으면 판단이 뭉치기 때문이다 — 썸네일의 근거와 가격의 근거가
한 칸에 섞이면 나중에 어느 쪽도 판정할 수 없다(D-18과 같은 문제).

**진행 판정은 화면이 하지 않는다.** `v_listing_ready`가 한다. 화면과 에이전트가
같은 기준을 봐야 해서다.

**단계마다 근거를 행으로 남긴다** — `listing_step_notes(step, note, hypothesis,
primary_metrics)`. `product_change_history`(026)와 모양이 같아서 등록 전 판단과
등록 후 수정이 한 줄로 이어진다.

`primary_metrics`는 **화면이 자동으로 박는다**(`LISTING_STEP_METRICS`, 86-listing.js).
낱말을 워커의 `PRIMARY_METRICS`와 **똑같이** 쓴다(`views`·`visitors`·`conversion_rate`·
`cart_adds`·`item_winner_rate`) — 다른 어휘를 쓰면 등록 전 근거와 등록 후 이력이
서로 다른 말이 되어 한 줄로 못 잇는다.

| 단계 | 봐야 할 지표 |
|---|---|
| 상품명 · 검색어 · 카테고리 · 대표이미지 | `views` · `visitors` (유입이 움직여야 맞다) |
| 상세페이지 | `conversion_rate` · `cart_adds` (조회는 안 변해야 정상) |
| 가격 | `conversion_rate` · `item_winner_rate` |

**이미지는 후보를 다 남긴다** — 고른 것만 남기면 "무엇 대신 무엇을 골랐나"가 사라진다.
`listing_assets.is_selected` + `selected_at`/`unselected_at`이 교체 이력이다.

**옵션별로 갈리는 건 둘뿐이다**(사용자 확인 2026-08-21): 대표이미지 · 물류 입고 정보.
나머지는 상품 단위라 `listing_projects`에 둔다.

**카테고리 코드는 소싱 수집용과 등록용이 같은 체계다**(2026-08-21 실물 확인, 표본 1건):
등록된 상품의 `product_json.displayCategoryCode=62902` ↔ `categories.category_code='62902'`.
그래서 등록 카테고리 화면이 우리가 이미 가진 8,156행을 그대로 검색한다.
**어긋나는 사례가 나오면 여기를 가장 먼저 의심할 것.**

카테고리를 정하면 화면이 `category_meta` 큐를 자동으로 넣는다. 그 응답에
필수속성·고시정보·인증·`isExpirationDateRequiredForRocketGrowth`가 들어 있고,
뼈대·물류 단계가 그걸 읽는다 → 실측 구조는 `../api/coupang-open-api.md`.

**원가는 추정이다.** 옵션·가격 화면에 적는 1688 단가·개당 원가는 소싱 시점의 감이고,
확정 원가는 발주 후 청구서에서 `inventory_lots`로 들어온다. **확정이 나와도 추정을
덮지 않는다**(R-05) — 덮으면 "내 추정이 얼마나 틀렸나"를 SKU 단위로 집계할 수 없다.
`price_source`가 `sourcing`이면 소싱에서 넘어온 값, `manual`이면 여기서 사람이 넣은 값이다.

**크기 등급(`size_type`)은 mm 치수에서 자동 계산하지 않는다.** 쿠팡의 등급 기준을
아직 실물로 확인 못 했다(R-14). 사람이 고르고, 비면 설정의 기본 등급을 쓴다.
입출고비가 이 등급으로 갈리므로 틀리면 마진 추정이 통째로 어긋난다.

**입출고비 표가 없는 카테고리는 0으로 계산된다** — 그러면 마진이 실제보다 **좋게** 나온다.
화면이 "입출고비 표 없음(0으로 계산)"이라고 붙여서 말한다.

**바코드**: 기본은 쿠팡 발급(`barcode_mode='coupang'` = WING의 "상품 바코드가 없어요").
자체 바코드를 넣으면 이 시스템의 조인키가 두 벌이 된다(D-02).
→ 이 선택이 API의 어느 필드로 나가는지는 **아직 실물 미확인**(`skuInfo.originalBarcode` 추정).
   기존 상품들의 값을 먼저 조회해서 확인한 뒤 코드를 쓴다(R-12).

## 등록은 복제가 기본이다

최상위 23키 + 옵션 23키에 고시정보·필수속성까지 사람이 채우면 WING에서 하는 것과
다를 게 없다. 비슷한 기존 상품을 복제하면 배송·반품지·과세유형·고시정보·필수속성이
그대로 따라오고, 사람은 이름·가격·이미지·검색어·물류규격만 바꾼다.
**다품종 소량이라 비슷한 상품이 계속 나오는 구조**에 이게 맞다.

복제 규칙: **쿠팡이 발급하는 것은 지우고, 우리가 정하는 것은 남긴다.**
지울 것을 알려준 건 에러였다 — 조회한 몸통을 그대로 보냈더니 "중복된 바코드가
존재합니다"가 나왔다.

**놓치기 쉬운 자리 셋** (전부 복제하면 원본 값이 조용히 따라온다):
1. `rocketGrowthAdditionalInformation.rfmInboundName` — 상품 단위 입고 표기명
2. `rocketGrowthItemData.skuInfo.inboundName` — **옵션 단위** 입고 표기명 (별개다)
3. `skuInfo`의 규격·무게 — 새 상품 크기가 다르면 틀린 값으로 등록된다

세부 필드·단위·제약은 `../api/coupang-open-api.md`.

## 초안 — 보내기 전에 멈추는 자리

**등록은 되돌릴 수 없다.** 그래서 `product_drafts`에 세워두고 검토한 뒤 올린다.
[초안으로 저장]은 쿠팡에 아무것도 보내지 않는다.

초안과 등록이 **같은 수집·빌드 함수를 쓴다**(`pnCollect`/`pnBuildPayload`).
따로 만들면 "초안에서는 되는데 등록하면 다르다"가 생긴다.
이미지는 초안 저장 시점에 미리 올린다 — 파일 입력은 다시 열면 비어 있어서,
URL로 남기지 않으면 초안을 불러와도 이미지가 사라진다.

**쿠팡의 임시저장과는 다른 것이다.** 승인 요청 체크를 빼고 등록하면 쿠팡 쪽
임시저장 상태로 들어간다(상태 흐름: 생성 → 임시저장 → 승인요청 → 승인대기중 → 승인됨).
초안은 그보다 앞, **쿠팡에 보내기 전** 단계다.

## 채널이 상품마다 다르다

같은 옵션 안에 로켓그로스와 마켓플레이스(판매자배송) 가격이 **두 벌** 들어 있을 수 있다.
실측: 한 상품은 로켓그로스 7,500 / 판매자배송 13,000, 다른 상품은
`marketplaceItemData`가 **null**인 로켓그로스 전용이었다.

그래서 화면이 복제 원본의 구성을 보고 판매자배송 칸을 켜고 끈다.
**없는 채널의 칸을 남겨두면 사람이 값을 넣고 그게 조용히 버려진다.**

## 실험 기록 — 무엇을 봐야 하는지가 정해져 있다

지표가 깔때기 단계별로 있어서 **바꾼 것에 따라 봐야 할 지표가 다르다.**
썸네일을 바꿨는데 전환율만 보면 아무 결론도 못 낸다.

| 바꾼 것 | 봐야 할 지표 | 이유 |
|---|---|---|
| 썸네일 · 검색어 · 상품명 | 조회 · 방문자 | 유입이 움직여야 맞다 |
| 상세페이지 | 구매전환율 · 장바구니 | **조회는 안 변해야 정상**이다 |
| 가격 | 구매전환율 · 아이템위너 | 둘 다 움직인다 |

이 매핑을 `product_change_history.primary_metrics`에 **행마다 박아둔다** —
그래야 AI가 매번 추측하지 않는다. 화면도 같은 힌트를 띄운다.

가설은 **항목별로 따로** 받는다. 썸네일과 상세페이지는 노리는 지표가 달라서
가설 하나를 두 곳에 복사하면 어느 쪽도 판정할 수 없다.

한 요청에서 두 가지를 바꾸면 **이력이 두 행**이 된다. 섞인 변경은 원인을 못 가리므로
나중에 분석에서 빼려면 쪼개져 있어야 한다.

### 바꾸기 전 사진은 우리가 보관한다

`before_value`에 경로만 남기면 그림은 쿠팡에만 있고, 쿠팡이 지우면 "이전 썸네일이
뭐였나"를 영영 못 본다. 그래서 워커가 **PUT 직전에** CDN에서 내려받아
Supabase Storage(`product-images/archive/...`)에 넣는다. PUT 뒤에 받으면 늦다.

### 판단해도 되는지를 뷰가 말한다

`v_product_experiments`는 변경 1건이 한 행이고 전후 7일 지표가 붙어 있다.
**변경 당일은 전후 어느 쪽에도 안 넣는다** — 몇 시에 바꿨는지 모르므로 그날은 섞여 있다.
**전환율은 평균이 아니라 합계끼리 나눈다** — 일별 평균을 내면 조회가 적은 날이
과대 대표된다(3회 중 1건=33%가 300회 중 5건=1.7%와 같은 무게가 된다).

교란 요인을 같이 낸다: 같은 창의 다른 변경 · 품절 · 아이템위너 상실 · 광고 상태 변화.
이게 없으면 **AI가 잘못된 결론을 확신한다.**

`verdict` 컬럼이 판단 가능 여부를 말한다(`비교 가능` / `표본 부족` / `원인 불명` …).
숫자만 내놓으면 사람도 AI도 과신한다.

> **지금 규모**: 하루 조회 1,200 남짓이라 **대부분 "표본 부족"으로 나온다.**
> 뷰가 고장난 게 아니라 사실이다. 값어치는 SKU가 늘었을 때 쌓여 있을 기록이다.
