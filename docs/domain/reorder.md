# 재고 · 재발주 제안

> **언제 읽나**: 권장 발주 수량이 감과 다를 때. 기본값(리드타임·안전일수)을 튜닝할 때.
> **최종 검증**: 2026-08-19 (SKU 5종 시뮬레이션 — 추이 급증·중국창고 보유·신상품·판매중지)
> **관련 코드**: `web/js/60-inbound.js` `loadStock()`·`renderStock()`·`STOCK.defaults`

## 방침

다품종 소량에서 가장 큰 손실은 적자가 아니라 **품절**이다. 반대로 많이 사두면 재고에 현금이 묶인다.
사용자 방침: **"최대한 타이트하되 품절은 안 나도록, 판매 추이 보면서 점증/점감."**

## 일평균 — 추이가 자동으로 반영된다

```
일평균 = 최근 7일 평균 × 0.6 + 최근 28일 평균 × 0.4
```

최근에 잘 팔리면 7일 평균이 올라가 발주량이 늘고, 시들해지면 자연히 준다.
**사용자가 원한 "점증/점감"이 별도 규칙 없이 이 가중치 하나에서 나온다.**
28일만 쓰면 반응이 느리고, 7일만 쓰면 하루 튄 값에 휘둘린다.

실측: 최근 7일 4개/일 + 28일 평균 2.5개/일 → 3.4 (28일만 썼으면 2.5로 과소평가)

## 재주문점과 권장 수량

```
재주문점 = 일평균 × (리드타임 + 안전일수)
권장수량 = 일평균 × (리드타임 + 안전 + 보충주기) − 이미 가진 물량
```

**이미 가진 물량 = 쿠팡 + 운송중 + 중국창고 + 미도착.**
파이프라인을 다 빼야 이중 발주가 안 된다 — 특히 **미도착(아직 중국에도 안 온 것)을 빼먹으면
이미 주문한 걸 또 발주한다.**

MOQ보다 작으면 MOQ로 올린다.

## 판정이 두 갈래인 게 핵심

쿠팡 재고로 버틸 날이 재주문점보다 짧을 때:
- **중국 창고에 재고가 있으면 → "입고요청"**
- 없으면 → "발주 필요"

**창고에 있는 걸 새로 사는 건 돈과 시간을 모두 버리는 짓이다.**

## 리드타임은 실측을 쓴다

발주 요청일 → 그 로트가 쿠팡에 도착한 날의 평균.
```
SKU에 직접 넣은 값  →  없으면 실측  →  그것도 없으면 기본 14일
```
화면에 "실측"이라고 표시된다. **예측(설정값)과 실측을 나란히 두는 게 이 프로젝트의 방식이다** —
발주가 쌓일수록 제안이 정확해진다.

## 근거 없는 숫자는 내밀지 않는다

판매 이력이 없는 SKU는 **"데이터 부족"**으로만 표시하고 수량을 제안하지 않는다.
판매중지 SKU도 판정에서 뺀다.
**자신 있게 틀린 숫자를 주는 게 아무 말 안 하는 것보다 나쁘다.**

## 기본값

`STOCK.defaults` 한 곳에 모아뒀다.
```
리드타임 14일 · 안전 5일 · 보충주기 14일 · 이력 28일
```
**근거 없이 정한 값이다** — 실제 운영 데이터가 쌓이면 여기부터 튜닝한다.
나중에 SKU별로 내리려면 `my_skus.lead_time_days`·`safety_days`가 이미 있다.
