# 원가 모델

> **언제 읽나**: 원가가 이상할 때. 원가·이익 계산을 고칠 때. 로트를 건드릴 때.
> **최종 검증**: 2026-08-19 (실제 청구서 5종 + 브라우저 시뮬레이션)
> **관련 코드**: `web/app.js` `loadLotCogs()`·`calcMargin()`·출고 저장 · `db/migrations/015,016,019,020,021,022`

## 한 장 요약

```
발주(구매대행 청구서)          출고(배대지 작업비)         판매
  상품가 + 중국내배송            검수·포장·바코드            선입선출로 차감
  + 국제운임 + 통관              보통 개당 300원
  + 대행수수료                        ↓                        ↓
  ── 전부 환율에 포함 ──      unit_work_fee_krw          영업이익
        ↓
  unit_purchase_cost_krw  ──────────┴──→  unit_cost_krw (총합)
```

**원가는 두 번에 나눠 확정된다.** 그리고 **작업비 청구서가 쿠팡센터 도착 전에 온다**(사용자 확인)
→ 물건이 팔리기 시작할 땐 이미 원가가 확정돼 있다.
**그래서 소급 재계산 로직을 만들지 않는다** → D-04

## 국제운임·통관을 SKU별로 배분하는 문제는 존재하지 않는다

제트 청구서 비고: "구매비용, 환율보전료, CO, H/L, **LCL비용, 픽업비, 통관비가 모두 포함**된 금액
= 1688시스템가격 × 환율"

일반 직수입에서 가장 어려운 "컨테이너 운임 SKU 배분"이 이 구조엔 **아예 없다.**
처음엔 무게/금액/CBM 배분 기준을 설계하려다 불필요로 판명 — **다시 설계하지 말 것.**

배분이 필요한 건 **중국 내 배송비 하나뿐**이다(같은 판매자 주문 안에서 수량 비례).

## 환율이 두 개다 → D-03

| 용도 | 값(2026-08) | 성격 |
|---|---|---|
| 구매대행 | 320 → **310**(08-05부터) | 상품가+운임+통관+수수료 **전부 포함** |
| 작업비·배송비 정산 | 219.72 | 실환율에 가깝다 |

**주문 생성 시각에 고정된다** — 쿠플러스 공지: "8월 4일 중국시간 17시까지 요청된 주문건은 320,
이후 생성된 주문건부터 310 자동 적용". 그래서 **로트마다 저장한다.**
시스템이 "현재 환율" 하나만 들고 있으면 안 된다.

검산: 2026-06-26 청구서 협상후 총액 합 2,055.28 CNY × 320 = ₩657,689.6 → 서류값 ₩657,690 일치.

## 로트 — 선입선출의 단위

```
발주 줄(purchase_order_lines) 1개  →  로트(inventory_lots) 1개
                                       부분 출고하면 쪼개진다
```

**SKU가 없어도 로트는 만든다** → D-05. 상품 등록 전에 먼저 발주하는 경우가 있어서다.
물건의 존재와 상품 등록은 별개 사건이다.

| | SKU 없이 |
|---|---|
| 입고(도착 처리)·불량 처리·중국창고 재고 | 된다 |
| 한국 출고·판매 원가·재발주 제안 | 안 된다 (바코드 없으면 쿠팡에 못 보낸다) |

### 원가를 두 축으로 저장한다

```
unit_purchase_cost_krw   구매대행분 (발주 시 확정)
unit_work_fee_krw        배대지 작업비 (출고 시 확정)
unit_cost_krw            총합 — 이익 계산에 쓰는 값
```

총합만 두지 않는 이유: "작업비가 원가의 몇 %인가" 같은 걸 SQL로 바로 물어볼 수 있어야 한다(R-04).
`cost_breakdown`(jsonb)에는 CNY 원값·환율·배송비 배분액까지 남는다.

### 부분 출고하면 로트를 쪼갠다

100개 중 60개만 보내면 그 60개엔 작업비가 붙고 남은 40개는 안 붙는다 →
한 로트가 두 개의 개당 원가를 갖게 된다. 그래서 나가는 만큼을 **새 로트로 떼어낸다**(`split_from_lot_id`).
통째로 나가면 분할 없이 그 로트를 옮긴다.

**여러 발주에서 온 같은 SKU는 오래된 것부터 내보낸다**(정렬: `arrived_china_at` → 없으면 `ordered_at`).
실측: 91개(6/26분 51 + 7/02분 40) 중 60개 출고 → 6/26 로트 통째(2,560→2,860) + 7/02 로트에서 9개 분할(2,600→2,900).

## 중국 내 배송비 배분과 재배분 → D-11

같은 1688 판매자에게서 여러 옵션을 사면 **배송비가 하나로 붙는다**. 이걸 수량 비례로 나눈다.

**한 SKU가 취소되면 남은 것들이 다시 나눠 진다** — 판매자는 나머지를 여전히 보내므로
배송비는 그대로 나가기 때문이다. 그래서 **취소 환불은 상품가만** 하고, 남은 줄들의 개당 원가는 올라간다.

```
취소 전: 4옵션 24개가 배송비 9 CNY를 나눔 → 개당 (13 + 0.375) × 320 = 4,280원
취소 후: 3옵션 18개가 배송비 9 CNY를 나눔 → 개당 (13 + 0.5)   × 320 = 4,320원
```

취소는 물건이 오기 전에 일어나므로(출고·판매 전) 원가를 다시 계산해도 과거 이익이 안 흔들린다 —
**이 시점이 아니면 고칠 기회가 없다.**

## 판매에 원가를 붙이는 방법 — `loadLotCogs()`

결과는 **(날짜|옵션ID) 단위 개당 원가 맵**이고, `buildDailyRow()`와 `renderSales()`가
`calcMargin({ costKrw })`로 넘겨 쓴다. `costKrw`가 있으면 그걸 쓰고, 없을 때만 예전 방식
(소싱 탭에 손으로 넣은 CNY 원가 × 환율)으로 떨어진다. **두 값을 섞지 않는다.**

> 예전 경로(`loadItemMeta()` → `product_items` → `user_items.cost_cny`)는 소싱 DB를 거치는데,
> 그건 **다른 판매자 상품을 조사한 목록**이라 실제 판매 옵션과 겹칠 이유가 없다 → D-09.
> 그래서 원가는 사실상 늘 비어 있었다.

**미리 계산해 저장하지 않고 볼 때마다 계산한다.** 로트 원가는 출고 때 작업비가 붙으며 한 번
올라가는데, 매번 현재 로트 원가로 계산하면 소급 갱신 로직이 아예 필요 없다.

**판매 이력을 전량 읽는다.** 선입선출은 처음부터 순서대로 소진시켜야 맞다. 조회 기간만 읽으면
이미 팔려나간 옛 로트가 남은 것처럼 계산돼 원가가 낮게 나온다.

### 반드시 지킬 두 규칙 (2026-08-19 검증 중 발견)

**① 판매일보다 나중에 도착한 로트는 못 쓴다.**
안 막으면 시스템 도입 전 옛 판매가 최근 매입분을 끌어다 써서, **없던 원가가 생기고**
정작 최근 판매는 로트가 모자라게 된다.

**② 개당 원가는 "덮인 수량"이 아니라 그날 판매수량 전체로 나눈다.**
화면이 `개당원가 × 판매수량`으로 합계를 내기 때문이다.
```
8개 팔림 / 6개분 원가만 앎(17,160원)
개당 2,860 × 8 = 22,880원   ← 틀림. 없는 원가 5,720원이 생긴다
개당 2,145 × 8 = 17,160원   ← 맞음
```
이렇게 하면 합계가 **항상 실제로 아는 원가와 정확히 같다.** 모자란 만큼은 `short`로 남는다.

**반품(음수 수량)은 맨 앞 로트로 되돌린다** — 어느 로트에서 나갔는지는 알 수 없으니 근사다(D-08과 같은 한계).

## 개당 원가 검산 예시

2026-07-06 청구서, 참개빵 슬랑이 16개:
```
1688 결제분   ₩40,960 ÷ 16 = 2,560원   (128 CNY × 320)
검수·분류·포장                  200원
바코드·원산지                   100원
───────────────────────────────
개당 원가                     2,860원   ← 부가세 제외
```
부가세는 세금계산서 수취 시 매입세액(환급 대상)이라 **원가에 포함하지 않는다.**
