# 규칙

> **언제 읽나**: 규칙을 어겼다는 지적을 받았을 때, 새 규칙을 넣거나 뺄 때, 세션 마무리 회고 때.
> **최종 갱신**: 2026-08-21
> **자동 주입되는 요약**: `CLAUDE.md`의 규칙 절(제목 한 줄씩). 이 파일은 그 상세다.

## 이 규칙들이 스스로 발전하는 방식

규칙은 **"이러면 사고 난다"는 예측**이다. 예측이니까 맞았는지 틀렸는지를 재야 한다.

```
사고·재작업이 일어남        →  실측
회고: 막았나? 어겼나? 없었나?  →  오차
발동 +1 / 위반 +1 / 새 후보 / 강등  →  수정
```

**증거가 붙지 않는 규칙은 도태된다.** 그래서 규칙마다 발동·위반 이력을 센다.

**개수 상한**: 전역 5 · 습관 8 · 폴더별 각 4.
넘으면 늘리지 말고 **가장 약한 것을 내린다** — 규칙이 많아지면 각각의 무게가 줄기 때문이다.
새 규칙은 반드시 **실제 사고를 근거로** 들어온다. 추측으로 만든 규칙은 넣지 않는다.

**사용자가 `규칙!` 이라고 하면**: 이번 턴에 어긴 규칙을 짚고, 위반 이력을 올리고, 왜 안 지켜졌는지 한 줄 남긴다. 어긴 게 없다고 판단되면 그렇게 말하고, 사용자가 새 규칙을 준다.

## 전역 (절대) — 5개

### R-01 · `service_role`/`secret` 키를 어떤 파일에도 넣지 않는다
발단: 과거 대화에서 secret 키가 노출되어 폐기한 이력
적용: 전체. extension·web·scripts 모두 publishable key + 관리자 계정 로그인만 쓴다
발동 0 · 위반 0 · 상태 활성

### R-02 · 실행된 마이그레이션은 수정하지 않는다
새 번호로만 추가하고, `if not exists`/`drop ... if exists`로 **여러 번 실행해도 안전**하게 만든다.
발단: 초기 스키마 운영 관례
발동 다수(매 마이그레이션) · 위반 0 · 상태 활성

### R-03 · 데이터 무결성 키를 건드리지 않는다
- `user_items`/`item_calc`의 PK `(user_id, item_id)` 복합키 → 단일키로 바꾸면 멀티유저가 깨진다
- `item_history`의 `unique index (item_id, recorded_date)` → 같은 날 중복 수집 방지의 유일한 장치
- 쓰기 시 `on_conflict=user_id,item_id` → 빼면 사용자 간 데이터가 서로 덮어써진다(RLS는 읽기만 막는다)

발단: 멀티유저 구조 설계
발동 0 · 위반 0 · 상태 활성

### R-04 · 원본을 버리지 않는다
집계된 숫자만 저장하고 원본을 버리면 나중에 "왜 이 숫자가 나왔는지" 역추적할 수 없다.
청구서 원문(`raw_line`), 원가 구성(`cost_breakdown`), CNY 원값과 환율을 항상 함께 남긴다.
발단: AI 에이전트가 나중에 분석한다는 전제(사용자 명시)
발동 다수 · 위반 0 · 상태 활성

### R-05 · 추정과 확정을 구분해서 저장한다
값 하나만 덜렁 두지 말고 어떤 방법으로 나온 값인지 남긴다.
예: `cost_status`(estimated/confirmed) · `invoice_source`(xlsx/manual/none) · 예치금 `status`(expected/confirmed/void) · `estimated_amount_krw` vs `amount_krw`
발단: 확정 정산과 옵션별 추정이 섞여 구분이 필요해짐
발동 다수 · 위반 0 · 상태 활성

## 습관 (작업 방식) — 8개

### R-10 · 애매하면 묻는다 — 질문에는 항상 제안을 붙인다
**반드시 물어야 하는 상황**
1. 새 테이블·컬럼을 만들 때 — 되돌리기가 비싸다
2. 계산식·회계 규칙을 정할 때 — 원가·이익·배분. 틀리면 조용히 어긋난다
3. 실무 순서를 코드로 옮길 때 — 단계·누가 언제 무엇을
4. 이미 쓰고 있는 화면의 동작을 바꿀 때
5. 외부 파일·API 구조를 가정할 때
6. 기본값을 정할 때 — 안전재고·보충주기 같은 숫자

**묻지 않아도 되는 것**: 변수명 · CSS 세부 · 커밋 메시지 · 이미 확정된 규칙의 재확인

**질문에는 항상 `> 제안:`을 붙인다.** 제안이 있으면 사용자가 "제안대로"로 넘길 수 있어 질문이 진행을 막지 않는다. **질문의 비용을 없애는 것이 규칙을 지키게 만드는 핵심이다.**

발단: 규칙이 있는데도 안 지켜진다는 사용자 지적(2026-08-19). 원인은 ①위치가 문서 끝 ②"애매하면"이 추상적 ③질문이 진행을 막음 — 셋을 각각 위치·트리거·제안첨부로 해결
발동 다수 · 위반 다수(2026-08-19 이전) · 상태 활성

### R-11 · 작업·결정 턴 끝에 `확인 필요` 또는 `가정 없음`을 적는다
가정을 했으면 반드시 드러낸다. 없으면 "가정 없음"이라고 쓴다. 침묵으로 넘어가는 걸 막는 장치.
**단순 질문 답변 턴에는 붙이지 않는다** — 소음이 되면 무시하게 된다.
발단: R-10과 같음
발동 0 · 위반 0 · 상태 활성(2026-08-19 신설)

### R-12 · 외부 파일·API 구조는 실물을 확인한 뒤 코드를 쓴다
발단: 2026-08-18~19 구매대행 청구서 구조를 **세 번 연속 잘못 가정**. 매번 "이번엔 파악했다"고 생각했고 매번 새 형태가 나왔다. 그리고 `--products` 동기화가 필드명을 문서만 보고 짜서 **1년 가까이 조용히 0행을 넣고 있었다**
적용: 파서 · API 연동 · 외부 서류 인식
발동 다수 · 위반 5 · 상태 활성
2026-08-21 회고: 정찰로 legalAgreement·가격 경로·skuInfo 단위를 확정한 건 발동이고,
화면 주소를 API 주소로 착각한 것과 응답 중첩 안쪽을 안 보고 "물류 필드 없음"이라
단언한 건 위반이다. **최상위 키만 훑는 것은 실물 확인이 아니다.**

### R-13 · 내놓기 전에 실제로 돌려본다 — 화면은 브라우저에서, 서버 코드는 문법 검사로

## 폴더별 — 각 4개 이하

### web/
1. 마진 계산은 `calcMargin()` 하나로 통일한다 — 다른 곳에서 계산식을 새로 쓰지 않는다
2. `recalcRow()`의 디바운스(600ms)를 제거하지 않는다 — 타이핑마다 API가 나간다
3. 프레임워크·번들러를 도입하지 않는다 — 사용자가 "복잡한 과정 없이"를 명시. `api/*.js`는 예외
4. 확장프로그램 호출(`syncSalesViaExtension`)이 실패해도 판매현황은 항상 동작해야 한다

### db/
1. 마이그레이션은 항상 멱등하게 (R-02의 폴더판)

### extension/
1. `trends/search` 요청 바디를 직접 만들지 않는다 — `interceptor.js`가 캡처한 실제 요청을 재사용
2. 조기 중단 조건을 완화하지 않는다 — 로켓 배지가 뒤에 나올 수 있다
3. 주입 함수(`page*`)에서 `throw`하지 않는다 — 크롬이 결과를 `null`로 만들어 에러가 사라진다. `{ok:false, error}` 반환
4. `RateGovernor` 임계값 · WING 동기화 "오늘+어제" 범위 · `pageSize`(10)를 감으로 조정하지 않는다
