# 의사결정 이력 + 안전장치 설계 + 사용자 요구사항

> '왜 이렇게 했는가'와 '무엇을 검토했다가 버렸는가'.

## 4. 의사결정 기록 (변경 이력 포함)

### 수집 방식
**확장프로그램 채택.** 이미 로그인된 브라우저 세션을 그대로 쓰므로 인증 문제가 사라진다.
기각: 노코드 스크래퍼(계정을 외부에 넘겨야 함), Playwright 직접구축(로그인·안티봇 부담), Claude in Chrome(유료·대량 부적합).

### 요청 템플릿
**처음** 바디를 직접 구성 → HTTP 400 반복 → **변경** interceptor로 실제 요청을 통째로 캡처해 카테고리 코드·검색어만 치환.
이유: Windows cURL 이스케이프(`^\^"`)를 눈으로 읽어 구조를 재구성하다 `context` 위치를 두 번 틀렸다.

### 이력 저장
3안 검토 후 **현재상태 + 변경분 분리** 채택.
- A(덮어쓰기): 추이 분석 불가 → 기각
- B(이력만 누적): 30만 행에서 "최신 행 골라내기"가 매번 느림 → 기각
- **C(분리)**: 목록은 `products`만 읽어 빠르고, 추이는 `item_history`

**변경분만 저장하는 이유(비용 계산)**
```
매일 전량 저장  연 1억 950만 행 → 15~20GB → 월 4~6만 원
변경분만(15%)   연 1,640만 행  → 2~3GB   → 기본 플랜 내
```
같은 날 중복은 DB의 `unique index (item_id, recorded_date)`가 막는다. 사용자: "날짜 단위 수집이라 같은 날짜 데이터는 필요 없다".

### 상품 vs 옵션 단위
**처음** 옵션 하나로 → **중간** 상품 통합 검토 → **최종 분리**(`products` + `product_items`)
결정적 근거: 사용자가 **"옵션별로 판매량·이미지가 다르다"**고 확인. 실제 데이터에서도 옵션마다 `imagePath`가 다름.

**정렬 기준**: 사용자 요구 — "A옵션 200, B옵션 100이면 300으로 솔팅되면 안 되고 200 이상에만 걸려야 한다" → `max_sales`. 다만 합계도 쓰고 싶다 하여 `sum_sales`도 저장해 화면에서 선택.

**대표 이미지**: 판매량 최대 옵션의 것.

### 사용자 편집값 보호
`user_items`를 **별도 테이블로 완전 분리.** 수집이 `product_items`를 아무리 덮어써도 원가·메모·즐겨찾기가 안전하다.

### want_price
**처음** 기본값 = currentPrice → **변경** 기본값 공백, 입력했을 때만 저장.
사용자 설명: "wantprice의 원래 목적은 내가 금액을 변경했을 때 입출고비와 수수료가 얼마나 나오나 알기 위한 것" → 두 벌 계산 구조로.

### 환율
**입력 시점 환율을 함께 저장**(A안). 사용자 표현 "그때 내가 했던 걸로 적용".
"현재 환율로 일괄 갱신" 버튼은 별도로 두기로 했으나 **미구현**.

### 인증·권한
**처음** service_role 키 → **변경** publishable key + 관리자 계정 로그인.
이유: 확장프로그램은 로컬 파일이라 누구나 열어볼 수 있고, service_role은 RLS를 통째로 우회한다.
```
is_admin = true   공통 데이터 쓰기 (확장프로그램이 이 계정으로 로그인)
is_admin = false  읽기만 + 본인 소싱 데이터
is_admin은 스스로 부여 불가 (RLS로 차단, SQL로만)
```

### 공개 범위
**처음** 혼자 사용 → **변경** 초대받은 회원만.
사용자: "회원가입 한 사람이 공통된 데이터도 볼 수 있으면서 자기만의 데이터도 관리할 수 있게"
→ `user_items`, `item_calc`의 PK가 **`(user_id, item_id)` 복합키**. 단일키로 되돌리면 멀티유저가 깨진다.
초대는 **이메일 등록 방식**(초대 코드 방식 기각 — 관리 편의).

### 카테고리 즐겨찾기
사용자별 (`user_category_favorites` 별도 테이블).

### 웹에서의 수집 실행
웹사이트는 CORS·쿠키 격리로 `wing.coupang.com`에 접근 불가 → **대기열 방식**
```
웹에서 선택 → collect_queue에 pending → 확장프로그램이 30초마다 확인 → 수집 → done
```

### 엑셀 IMAGE 수식
**처음** `=IMAGE(url,4,300,300)` → 엑셀에서 `#VALUE!` → **원인**: 두 프로그램 인자 순서가 다름
```
구글시트  IMAGE(url, mode, height, width)            mode 4 = 사용자지정
엑셀      IMAGE(source, alt, sizing, height, width)  sizing 3 = 사용자지정
```
→ **해결**: 드롭다운으로 선택. 기본값은 **양쪽 호환**(`=IMAGE(url)`).

### 웹사이트 기술
**단일 HTML + Vanilla JS 채택.** Next.js는 지금 단계에서 배울 게 많아 기각(나중에 전환 가능). 로우코드(Retool 등)는 "다른 기능 추가"에 한계.
Supabase를 DB/API로 두면 **웹사이트를 나중에 갈아엎어도 데이터가 남는다**는 게 채택 근거.

### IP 로테이션 / 프록시
**기각(보류).**
1. 현재 구조에서 쿠키 유지 + IP만 변경 = **차단이 오히려 빨라짐**(Akamai가 세션-IP 불일치를 강한 신호로 봄)
2. 제대로 하려면 IP별 독립 세션 → Node.js 이전 필요
3. 데이터센터 프록시는 즉시 차단, 주거용은 전송량 과금이라 비용 큼
→ 조기중단·중복제거로 트래픽을 1/4로 줄이는 게 선행되어야 한다.

### 속도 설정
사용자가 "분당 1000?"이라 물었을 때 **권하지 않았다.** 탐색 시작점이 300(초당 5건)이라 이미 위험 구간이고, 15건마다 평가하는데 분당 300이면 15건이 3초라 서버 반응 전에 다음 단계로 올라간다. 또 최대 동시 5·간격 1500ms로는 분당 200이 한계라 **숫자만 크고 실효가 없다.**
**권장: 분당 100~150, 최대 동시 5, 간격 1000ms**

## 6. 안전장치 설계 요약 (수치는 코드 참조)

### RateGovernor — 5개 신호원 4단계 경보
```
신호: 응답추세(1.4/1.8/2.5배) · 변동성(p95>3.5배) · TTFB(2/3배)
      방어쿠키(_abck에 ~[1-9]~) · 리다이렉트 · 능동탐침 · 표적견제 · HTTP429/403

대응: 1 주의 간격+0.25 / 2 경고 동시-1·상한×0.8 / 3 위험 동시→1·60초냉각
      4 차단 60~600초 정지(지수) · 연속 4회면 완전중단
회복: 정상 20건 연속 → 동시+1
```
**표적견제**가 특히 유용하다 — 탐침은 정상인데 본 요청만 느리면 "너를 골라서 늦추는 중"이라는 강한 신호.

**임계점 자동 탐색**: 분당 상한의 30%에서 시작, 15건마다 평가, 응답이 기준의 1.3배로 나빠지면 **직전 값의 75%를 안전선으로 고정.**

### 조기 중단
```
중단 조건 = salesOk && deliveryResolved && priceOk   (MIN 50KB, MAX 400KB)
```
> **`판매자:`만 있고 `배송사:`가 없으면 중단하지 않는다.** 로켓 이미지가 뒤에 나올 수 있어 오분류를 막기 위함. 이 조건을 완화하지 말 것.

실측: 560KB → 평균 395KB

## 10. 사용자 요구사항·취향

### 작업 방식 (사용자가 명시적으로 요구)
- **검증 없이 코드를 내지 말 것.** 정규식·계산·SQL을 실제 샘플로 검증한 뒤 적용했다. 특히 **파일에 반영된 코드를 그대로 추출해서 재검증**하는 방식을 썼다.
- **진단 기능을 함께 만들 것.** "오류가 나지 않는지 확인할 수 있는 것들을 너한테 다시 보내주면 검증하고, 확인하기 쉽게 하는 기능도 넣어도 돼" → 현재 진단 버튼 13개.
- **한 번에 다 하지 말고 나눌 것.** "한꺼번에 다 하는 게 어려울 것 같으면 나눠서 해도 돼"
- **차단을 최대한 피할 것.** "차단 당할 것 같은 기미나 그런 감지를 최대한으로 해서 안전하고 빠르게"

## 2026-08-12 — 소싱 목록의 배송유형을 옵션 실제값으로

**문제** — 목록의 '배송' 칸이 `products.has_rocket` boolean 하나로 "로켓/일반"만 찍었다. 실제 유형(로켓배송·로켓프레시·로켓직구·판매자로켓·판매자배송)은 옵션(`product_items.delivery_badge`)에만 있었고, 배송유형 필터는 걸 컬럼 자체가 없어 아예 동작하지 않았다.

**택하지 않은 안**
- *조회할 때 product_items를 조인/추가조회* — 페이지(40행)마다 왕복이 하나 더 생기고 옵션 수만큼 행이 딸려온다. 배송유형은 수집할 때만 바뀌는 값이라 매번 계산할 이유가 없다.
- *확장프로그램이 products에 대표 유형을 채우기* — 1단계(목록만) 수집처럼 배송 정보가 없는 업로드가 기존 값을 덮어써 지운다.

**택한 안** — `products.delivery_badges text[]`에 미리 접어두고, `product_items`의 statement 트리거가 갱신한다(004). 목록 조회는 추가 요청 0회, 필터는 GIN 배열 포함검색.

**섞여 있을 때** — 사용자 선택: 하나로 줄이지 않고 **옵션에 존재하는 유형을 전부 표시**. 예) 판매자배송 3개 + 판매자로켓 1개 → 두 배지 모두 표시. 순서는 `delivery_badge_rank()`로 로켓 계열 먼저.

**정규화** — 수집 라벨 표기가 제각각이라 5종으로 접되, 못 알아본 라벨은 판매자배송으로 몰지 않고 원문 그대로 남긴다("실제 옵션에 있는 값"이 화면에 보여야 하므로). `'판정불가'`는 정보 없음으로 보고 제외 → 배지가 하나도 없으면 `—`.

**같이 한 조회 최적화(기능 변경 없음)**
- 인덱스: `(max_sales desc) where is_active`, `(category_code, max_sales desc) where is_active`, 상품명 검색용 pg_trgm GIN. 상품명 검색은 그동안 인덱스가 없어 전체 스캔이었다.
- 옵션 펼치기: `product_items` → `user_items` 순차 2회를 `product_id`로 동시 요청 2회로 (user_items에도 product_id가 있고 `(user_id, product_id)` 인덱스가 이미 있다).
- 카테고리 필터 8000여 개 `<option>`을 createElement 루프 대신 문자열 한 번에 삽입, `full_path`는 정렬에만 쓰이므로 select에서 제외.
- 무한 스크롤 핸들러가 스크롤마다 `$('.main')`을 다시 찾던 것 캐시 + passive.

## 2026-08-13 — 판매현황 탭: 쿠팡 공식 Open API 연동

사용자가 "오늘 이익금/판매량/수수료를 사이트에서 보고 싶다"고 요청. 지금까지 쓰던 내부 역공학 API(로그인 쿠키 기반)와는 완전히 별개인 **쿠팡 공식 Open API**(`developers.coupang.com`, HMAC 인증)를 새로 붙이는 작업.

### 호출 위치: Vercel 서버리스 → (실패) → GCP VPS

**처음(Vercel 서버리스 함수)**: `web/`이 이미 Vercel에 있으니 `web/api/sales-today.js` 하나만 추가하면 끝일 줄 알았다. secretKey는 여기 환경변수에만 두고 서명·호출까지 서버에서 처리.

**막힘 1 — IP 화이트리스트**: 쿠팡 Open API는 accessKey 발급 시 WING에 등록한 IP(최대 10개)에서만 호출을 허용한다. Vercel 서버리스는 호출마다 AWS 유동 IP 풀에서 아무거나 쓰므로 등록 자체가 불가능 — 명확한 JSON 403(`"Your ip address ... is not allowed"`).

**막힘 1 우회 시도(유료 고정IP 프록시) — 실패**: Webshare(데이터센터 프록시)에서 고정 IP를 사서(`undici`의 `ProxyAgent`로 Vercel 함수가 그 IP를 거쳐 나가도록) WING에 등록. 처음엔 성공(200 OK)했으나, 곧 **다른 종류의 차단**이 시작됨 — JSON이 아니라 쿠팡 로고가 박힌 HTML "Access denied" 페이지. 이건 화이트리스트(accessKey 단의 검사)가 아니라 그 앞단의 **WAF/CDN이 IP 평판으로 차단**하는 것으로 보였다. **IP를 두 개 바꿔봐도 동일하게 차단** — 개별 IP가 아니라 그 프록시 업체의 IP 대역 자체가 이미 블랙리스트에 있는 것으로 결론. QuotaGuard(더 비싼, "기업 API 화이트리스트 통과" 전문 업체) 무료체험까지 고려했으나, 그 전에 근본적으로 재검토함.

**핵심 재검토**: 애초에 이런 서비스형 프록시를 사는 것 자체가 "서버리스를 굳이 쓰기 위한 우회로"였다. 실제 쿠팡 API 연동 사례들은 보통 **자기 서버(사무실/VPS)에서 직접 호출** — 그런 서버엔 원래 고정 IP가 기본으로 딸려 나와서 이 문제 자체가 없다.

**최종(현재)**: GCP `e2-micro` 무료 티어 VPS 하나를 만들어(리전 `us-west1`, 외부 IP 예약해서 고정) 거기서 `scripts/rocket-growth-sync.js`가 cron으로 직접 쿠팡을 호출한다. 프록시도, Vercel 함수도 더는 안 쓴다. 그 IP를 WING에 등록했더니 **화이트리스트도, WAF도 둘 다 통과** — Webshare 데이터센터 IP와 GCP IP의 차이로 추정(GCP는 정상적인 클라우드 사업자 IP라 프록시 업체 블랙리스트에 없는 듯).

`web/api/sales-today.js`/`PROXY_URL`은 실패한 1차 시도의 잔재지만 지우지 않고 남겨뒀다(폴백용, 필요해지면 재사용 가능).

### 데이터 흐름: 왜 웹이 쿠팡 API를 직접 안 부르고 Supabase를 거치나

VPS가 매번 웹 요청에 실시간으로 응답하는 서버를 띄우는 대신, **주기적으로(cron, 30분) 쿠팡을 불러서 Supabase 테이블(`rocket_growth_sales_daily`)에 저장**해두고 웹은 그 테이블만 읽는다. 확장프로그램이 이미 이 패턴("수집기가 쓰고 웹은 읽기만")이라 구조적으로 통일된다. 부가 이점: 쿠팡 API가 느리거나 잠깐 막혀도 웹 페이지 로딩엔 영향 없음.

### 수수료·입출고비: 추정치로 확정

로켓그로스 Open API 어디에도 수수료·정산액 필드가 없다(주문 API는 수량·단가까지만). 마켓플레이스 전용 정산 API 2종(`revenue-history`, `settlement-histories`)도 문서로 직접 확인했으나 로켓그로스 대상이 아니고 입출고비 개념 자체가 없음(그 비용은 로켓그로스=쿠팡 풀필먼트에만 발생). **API로 정확한 값을 받을 방법이 없다는 게 확정** — 요금표 기반 추정(`feeFor()`+`calcMargin()`, 기존 소싱 페이지와 동일 로직 재사용)이 유일한 방법이고 이 이상 찾아볼 필요 없음.

### 카테고리별 수수료율: 있던 문제를 이 김에 같이 해결

같은 맥락에서 사용자가 WING의 "수수료 안내" 페이지(HTML, `2019-11-25 기준` 명시)를 직접 가져다줌 — 이걸 파싱해서 `categories.commission_rate`를 채우고 전역 10.8% 가정치를 완전히 없앴다(`db/migrations/006`, `007`).

**함정**: 그 페이지의 대분류 표기(가전디지털, 가구/홈인테리어, 문구/사무용품, 출산/유아, 스포츠/레저용품, 패션)와 실제 `categories.root_name`(가전/디지털, 가구/홈데코, 문구/오피스, 출산/유아동, 스포츠/레져, 패션의류잡화)이 **6개나 달랐다.** 표기를 그대로 믿고 매칭했으면 전체 카테고리의 63%가 조용히 매칭 안 된 채로 넘어갈 뻔했음 — 실행 전에 실제 DB를 전수조회(`select root_name` 8,156행)해서 대조하고서야 발견. **교훈: 외부 자료의 이름 체계를 절대 그대로 믿지 말 것.**

**부수 발견 버그**: 그렇게 고치고도 일부 카테고리("뷰티"인데 수수료가 안 뜨는 등)가 여전히 안 됐다 — 원인은 `categories.root_name`이 마이그레이션 002에서 **딱 한 번만 백필**됐을 뿐 자동으로 유지되는 게 아니어서, 그 이후 새로 수집된 카테고리는 `full_path`는 정상인데 `root_name`만 계속 null로 남는 것이었다(`db/migrations/008`이 트리거로 고침). `delivery_badges`와 똑같은 "원본→파생 캐시, 트리거로 유지" 패턴을 안 따르고 있었던 게 원인 — 새로 파생 컬럼을 만들 땐 이 패턴을 반드시 따를 것.

### 계산 타이밍 버그 (같은 세션에서 2번 발견)

`state.readyForMargins`(설정·요금표 로딩 완료 시그널)에 카테고리 로딩(`loadCategoryOptions()`)이 빠져 있었다 — commission이 이제 `state.catUnits`에 의존하게 되면서(예전엔 fee 조회만 이걸 썼고 실패해도 무해했음) 페이지를 열자마자 너무 빨리 상품을 보면 "수수료 정보 없음"으로 **영구히 굳어버리는**(한 번 계산되면 다시 안 됨) 문제가 소싱 목록과 옵션 펼치기 두 군데서 각각 발견됨. `readyForMargins`에 `loadCategoryOptions()`를 포함시켜 해결 — **새로운 비동기 로딩 상태를 추가할 때마다 이 프로미스에 포함시켜야 하는지 항상 확인할 것.**

## 2026-08-15~16 — 판매현황: 확정 정산 정확도 개선 (UI 재구성 + 상품별 실제 원가)

기존 판매현황(2026-08-13/15 완성분)은 WING 위젯 실측치와 계속 어긋났다. 사용자가 여러 라운드에 걸쳐 실제 스크린샷·DB 조회로 원인을 하나씩 짚어가며 고친 세션 — 개별 버그의 증상/원인/해결은 `docs/troubleshooting.md` 23~26번, API 스펙은 `docs/api-notes.md` 4-4-5/4-4-6. 여기는 **왜 이런 설계를 택했는지**만.

### UI를 카드 1벌 → 3단 구조로 재구성한 이유
예전엔 "확정 정산 요약" 카드(전체 합계) + "오늘 판매현황" 카드(추정) 2벌이 따로 있어서, 조회 기간을 바꿔도 상단 요약이 뭘 반영하는지 헷갈렸다. **상단(고정기간: 이번 달/이번 주/최근 7일/오늘) / 중단(조회 기간의 일별 상세) / 하단(조회 기간의 상품별 상세)**로 나눠서 "항상 보이는 것"과 "조회로 바뀌는 것"을 분리했다. 확정치와 추정치를 섞어 보여주되(사용자: "따로 추정치라고 표시할 필요는 없어") 화면에 라벨을 안 붙이기로 함 — 대신 코드 주석·CLAUDE.md에 어디가 확정이고 어디가 추정인지 남김.

### "정산 백필"과 "상품 원가정보 갱신"을 자동이 아니라 수동 버튼으로 만든 이유
둘 다 WING을 여러 번(전자는 날짜 수만큼 순차, 후자는 페이지 수만큼 순차) 호출한다. 판매현황 탭을 열 때마다 자동으로 돌리면 느리고 WING에 부담이다(요금 API의 `RateGovernor` 안전장치와 같은 우려). 사용자가 직접 "몇백 개 상품이 될 수 있다"고 확인해줘서, 자동화는 아예 검토하지 않고 수동 버튼으로 확정.

### 상품별 원가정보를 덮어쓰지 않고 이력(스냅샷)으로 쌓기로 한 이유
처음엔 상품당 최신값 하나만 유지(upsert)하는 게 단순해 보였다. 그런데 **가격을 바꾸면 개당 수수료·입출고비도 같이 바뀌는데, 가격 변경 전에 팔린 것은 변경 전 요율로 계산해야 한다**는 게 사용자의 명확한 요구였다 — "내가 1번 말한 걸 잘 생각해서 구현 방향을 다시 말해봐"라고 재확인까지 받음. 그래서 `(vendor_item_id, captured_at)`로 이력을 쌓고, 판매 날짜 이전 중 가장 최근 스냅샷을 골라 쓰는 as-of 매칭(`snapshotAsOf()`)으로 설계했다.

**`trigger_source` 컬럼을 미리 넣어둔 이유**: 사용자가 "가격 수정 기능도 나중에 웹에서 만들 건데, 그때는 가격을 바꾼 바로 그 순간이 사람이 버튼 누르는 것보다 훨씬 정확한 스냅샷 시점"이라고 제안. 지금은 항상 `'manual_refresh'`뿐이지만, 나중에 가격 수정 기능이 생기면 그 상품 하나만 `'price_change'` 소스로 자동 스냅샷을 찍도록 확장할 계획이라 컬럼만 미리 마련해뒀다(나중에 추가하려면 마이그레이션을 또 해야 해서 지금 넣는 게 쌈).

### as-of 매칭에 "참고용(2순위)" 폴백을 추가한 이유
설계상 스냅샷 이전 판매는 카테고리 추정으로 폴백하는 게 "정확한" 동작이었다. 그런데 이 계정은 카테고리 매칭 자체가 안 되는 상품이 많아서(기존 이슈), 과거 날짜가 전부 "수수료 정보 없음"으로 나왔다. 사용자가 "옛날 것도 빈칸보다 값이 있어야 정산현황과 맞는지 검증하기 편하다"고 명시적으로 요청 → 이전 스냅샷이 없으면 있는 것 중 가장 가까운(시간상) 스냅샷을 대신 쓰고 "(참고용)"으로 구분 표시하도록 완화. **정확도보다 검증 편의를 택한 의도적 타협**이라는 걸 잊지 말 것 — 프로덕션에서 진짜 정확한 과거 수치가 필요해지면 이 폴백을 다시 검토해야 한다.

### 순이익 vs 영업이익을 분리한 이유
사용자 정의: **순이익 = 매출 − 수수료 − 입출고비 − 쿠폰비 − 보관비(배분)**, **영업이익 = 순이익 − 원가 − 배송·작업비**(보관비는 영업이익 계산에서 제외). 왜 보관비만 빼는지 명시적 설명은 못 들었지만("영업이익은 원가 + 쿠팡까지의 배송비" 라는 표현으로 확인), 보관비는 원가·배송비와 성격이 달라(재고 보유 비용이지 상품 원가/배송비가 아님) 사용자의 영업이익 정의에서 의도적으로 제외된 것으로 보임 — 코드에도 그대로 반영(`web/CLAUDE.md`).

## 2026-08-17 — 상품/옵션별 상세표 vs 일별 상세표 수수료·입출고비·순이익 불일치 조사

사용자가 8/16 기준으로 "매출·쿠폰비는 맞는데 수수료+입출고비·순이익이 다르다"고 지적. 라이브 DB에서 그날 판매 4건의 원가 스냅샷과 확정 정산 원본을 직접 대조해서 원인을 산술로 검증했다(코드 추측이 아니라 실측 대조로 확정 — 이 프로젝트의 기존 관례를 그대로 따름).

### 원인 1(해결): 상품별 원가 스냅샷은 부가세 별도, 확정 정산은 부가세 포함
스냅샷 기반 수수료 합(3,758원) × 1.1 = 4,134원 — 그날 확정 수수료(4,134원)와 **정확히 일치**. 스냅샷의 `commission_amount`/`fulfillment_amount`는 WING 재고현황 "예상(개당)" 툴팁 값인데, 이건 부가세 별도 표기로 보인다. 반면 확정 정산 필드는 이름 자체가 `totalTakeRateAmountWithVat`/`totalCfsAmountWithVat`(부가세 포함)다. `withSnapshotVat()`(×1.1)를 스냅샷 기반 수수료·입출고비 계산에 적용해서 해결 — **카테고리 요율 폴백(commissionFor/feeFor)에는 적용 안 함**(그쪽은 부가세 포함 여부를 검증한 적 없어서, 근거 없이 같은 보정을 씌우면 새 오차를 만들 수 있음). 쿠폰비(coupon_amount)도 보정 대상 아님 — 보정 없이 이미 정확히 일치했음(8/16 실측).

### 원인 2(구조적 한계, 부분 완화만): 순수량 0이 된 옵션의 반품처리비가 상품별 집계 어디에도 안 잡힘
VAT 보정 후에도 입출고비가 여전히 차이 남(8/16: 9,368원). 이유: WING 판매목록(`sold-vendor-item-list`)은 **당일 매입+당일 반품으로 순수량이 정확히 0이 된 옵션을 목록에서 통째로 제외한다**(0으로 안 찍히고 아예 없음, `docs/troubleshooting.md` #26에서 처음 발견된 패턴과 동일 원인). 그 옵션의 반품처리비는 확정 정산(계정 전체 합계)엔 포함되지만, 저희는 "그날 팔린 옵션" 목록을 순회하는 구조라 애초에 계산 대상에 들어오지 않는다. **순수량이 0이 아닌 반품**(예: 어제 판 게 오늘 반품)은 이미 음수 수량 행으로 정상 반영되고 있어서, 문제는 이 좁은 net-zero 케이스뿐이다.

**검토한 해결 방향**:
- 상품별로 정확히 귀속(진짜 해결) — WING에 반품만 따로 보여주는 API(반품관리 등)가 있고 개별 반품 건(옵션ID+반품처리비)을 준다면 가능. **미착수, 다음 세션 이후 착수 예정** — WING 내부 API라 사용자의 브라우저 캡처가 필요함(기존 캡처 도구 재사용).
- 안분 배분(차액을 그날 판매 옵션들에 비례 배분) — 검토했으나 **채택 안 함**: 그 반품과 무관한 다른 옵션에 비용을 "배정"하는 셈이라 오히려 실제와 더 멀어지는 가짜 정밀도. AI 분석 지향 원칙("추정치와 확정치를 구분 가능하게")에도 안 맞음.
- **채택**: 상품별 합계와 확정 정산을 나란히 대조해서 차액을 투명하게 보여주기만 함(`renderReconcileNote()` 확장, 매출만 보던 걸 수수료+입출고비·순이익까지 넓힘) — 억지로 맞추지 않고 "이만큼 차이 나고 이유는 이거다"를 화면에서 바로 알 수 있게 하는 쪽을 택했다.
