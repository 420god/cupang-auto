# 의사결정 이력 + 안전장치 설계 + 사용자 요구사항

> '왜 이렇게 했는가'와 '무엇을 검토했다가 버렸는가'.

## 4. 의사결정 기록 (변경 이력 포함)

### 수집 방식
**확장프로그램 채택.** 이미 로그인된 브라우저 세션을 그대로 쓰므로 인증 문제가 사라진다.
기각: 노코드 스크래퍼(계정을 외부에 넘겨야 함), Playwright 직접구축(로그인·안티봇 부담), Claude in Chrome(유료·대량 부적합).

### 요청 템플릿
**처음** 바디를 직접 구성 → HTTP 400 반복 → **변경** interceptor로 실제 요청을 통째로 캡처해 카테고리 코드·검색어만 치환.
이유: Windows cURL 이스케이프(`^\^"`)를 눈으로 읽어 구조를 재구성하다 `context` 위치를 두 번 틀렸다.

### 이력 저장
3안 검토 후 **현재상태 + 변경분 분리** 채택.
- A(덮어쓰기): 추이 분석 불가 → 기각
- B(이력만 누적): 30만 행에서 "최신 행 골라내기"가 매번 느림 → 기각
- **C(분리)**: 목록은 `products`만 읽어 빠르고, 추이는 `item_history`

**변경분만 저장하는 이유(비용 계산)**
```
매일 전량 저장  연 1억 950만 행 → 15~20GB → 월 4~6만 원
변경분만(15%)   연 1,640만 행  → 2~3GB   → 기본 플랜 내
```
같은 날 중복은 DB의 `unique index (item_id, recorded_date)`가 막는다. 사용자: "날짜 단위 수집이라 같은 날짜 데이터는 필요 없다".

### 상품 vs 옵션 단위
**처음** 옵션 하나로 → **중간** 상품 통합 검토 → **최종 분리**(`products` + `product_items`)
결정적 근거: 사용자가 **"옵션별로 판매량·이미지가 다르다"**고 확인. 실제 데이터에서도 옵션마다 `imagePath`가 다름.

**정렬 기준**: 사용자 요구 — "A옵션 200, B옵션 100이면 300으로 솔팅되면 안 되고 200 이상에만 걸려야 한다" → `max_sales`. 다만 합계도 쓰고 싶다 하여 `sum_sales`도 저장해 화면에서 선택.

**대표 이미지**: 판매량 최대 옵션의 것.

### 사용자 편집값 보호
`user_items`를 **별도 테이블로 완전 분리.** 수집이 `product_items`를 아무리 덮어써도 원가·메모·즐겨찾기가 안전하다.

### want_price
**처음** 기본값 = currentPrice → **변경** 기본값 공백, 입력했을 때만 저장.
사용자 설명: "wantprice의 원래 목적은 내가 금액을 변경했을 때 입출고비와 수수료가 얼마나 나오나 알기 위한 것" → 두 벌 계산 구조로.

### 환율
**입력 시점 환율을 함께 저장**(A안). 사용자 표현 "그때 내가 했던 걸로 적용".
"현재 환율로 일괄 갱신" 버튼은 별도로 두기로 했으나 **미구현**.

### 인증·권한
**처음** service_role 키 → **변경** publishable key + 관리자 계정 로그인.
이유: 확장프로그램은 로컬 파일이라 누구나 열어볼 수 있고, service_role은 RLS를 통째로 우회한다.
```
is_admin = true   공통 데이터 쓰기 (확장프로그램이 이 계정으로 로그인)
is_admin = false  읽기만 + 본인 소싱 데이터
is_admin은 스스로 부여 불가 (RLS로 차단, SQL로만)
```

### 공개 범위
**처음** 혼자 사용 → **변경** 초대받은 회원만.
사용자: "회원가입 한 사람이 공통된 데이터도 볼 수 있으면서 자기만의 데이터도 관리할 수 있게"
→ `user_items`, `item_calc`의 PK가 **`(user_id, item_id)` 복합키**. 단일키로 되돌리면 멀티유저가 깨진다.
초대는 **이메일 등록 방식**(초대 코드 방식 기각 — 관리 편의).

### 카테고리 즐겨찾기
사용자별 (`user_category_favorites` 별도 테이블).

### 웹에서의 수집 실행
웹사이트는 CORS·쿠키 격리로 `wing.coupang.com`에 접근 불가 → **대기열 방식**
```
웹에서 선택 → collect_queue에 pending → 확장프로그램이 30초마다 확인 → 수집 → done
```

### 엑셀 IMAGE 수식
**처음** `=IMAGE(url,4,300,300)` → 엑셀에서 `#VALUE!` → **원인**: 두 프로그램 인자 순서가 다름
```
구글시트  IMAGE(url, mode, height, width)            mode 4 = 사용자지정
엑셀      IMAGE(source, alt, sizing, height, width)  sizing 3 = 사용자지정
```
→ **해결**: 드롭다운으로 선택. 기본값은 **양쪽 호환**(`=IMAGE(url)`).

### 웹사이트 기술
**단일 HTML + Vanilla JS 채택.** Next.js는 지금 단계에서 배울 게 많아 기각(나중에 전환 가능). 로우코드(Retool 등)는 "다른 기능 추가"에 한계.
Supabase를 DB/API로 두면 **웹사이트를 나중에 갈아엎어도 데이터가 남는다**는 게 채택 근거.

### IP 로테이션 / 프록시
**기각(보류).**
1. 현재 구조에서 쿠키 유지 + IP만 변경 = **차단이 오히려 빨라짐**(Akamai가 세션-IP 불일치를 강한 신호로 봄)
2. 제대로 하려면 IP별 독립 세션 → Node.js 이전 필요
3. 데이터센터 프록시는 즉시 차단, 주거용은 전송량 과금이라 비용 큼
→ 조기중단·중복제거로 트래픽을 1/4로 줄이는 게 선행되어야 한다.

### 속도 설정
사용자가 "분당 1000?"이라 물었을 때 **권하지 않았다.** 탐색 시작점이 300(초당 5건)이라 이미 위험 구간이고, 15건마다 평가하는데 분당 300이면 15건이 3초라 서버 반응 전에 다음 단계로 올라간다. 또 최대 동시 5·간격 1500ms로는 분당 200이 한계라 **숫자만 크고 실효가 없다.**
**권장: 분당 100~150, 최대 동시 5, 간격 1000ms**

## 6. 안전장치 설계 요약 (수치는 코드 참조)

### RateGovernor — 5개 신호원 4단계 경보
```
신호: 응답추세(1.4/1.8/2.5배) · 변동성(p95>3.5배) · TTFB(2/3배)
      방어쿠키(_abck에 ~[1-9]~) · 리다이렉트 · 능동탐침 · 표적견제 · HTTP429/403

대응: 1 주의 간격+0.25 / 2 경고 동시-1·상한×0.8 / 3 위험 동시→1·60초냉각
      4 차단 60~600초 정지(지수) · 연속 4회면 완전중단
회복: 정상 20건 연속 → 동시+1
```
**표적견제**가 특히 유용하다 — 탐침은 정상인데 본 요청만 느리면 "너를 골라서 늦추는 중"이라는 강한 신호.

**임계점 자동 탐색**: 분당 상한의 30%에서 시작, 15건마다 평가, 응답이 기준의 1.3배로 나빠지면 **직전 값의 75%를 안전선으로 고정.**

### 조기 중단
```
중단 조건 = salesOk && deliveryResolved && priceOk   (MIN 50KB, MAX 400KB)
```
> **`판매자:`만 있고 `배송사:`가 없으면 중단하지 않는다.** 로켓 이미지가 뒤에 나올 수 있어 오분류를 막기 위함. 이 조건을 완화하지 말 것.

실측: 560KB → 평균 395KB

## 10. 사용자 요구사항·취향

### 작업 방식 (사용자가 명시적으로 요구)
- **검증 없이 코드를 내지 말 것.** 정규식·계산·SQL을 실제 샘플로 검증한 뒤 적용했다. 특히 **파일에 반영된 코드를 그대로 추출해서 재검증**하는 방식을 썼다.
- **진단 기능을 함께 만들 것.** "오류가 나지 않는지 확인할 수 있는 것들을 너한테 다시 보내주면 검증하고, 확인하기 쉽게 하는 기능도 넣어도 돼" → 현재 진단 버튼 13개.
- **한 번에 다 하지 말고 나눌 것.** "한꺼번에 다 하는 게 어려울 것 같으면 나눠서 해도 돼"
- **차단을 최대한 피할 것.** "차단 당할 것 같은 기미나 그런 감지를 최대한으로 해서 안전하고 빠르게"

## 2026-08-12 — 소싱 목록의 배송유형을 옵션 실제값으로

**문제** — 목록의 '배송' 칸이 `products.has_rocket` boolean 하나로 "로켓/일반"만 찍었다. 실제 유형(로켓배송·로켓프레시·로켓직구·판매자로켓·판매자배송)은 옵션(`product_items.delivery_badge`)에만 있었고, 배송유형 필터는 걸 컬럼 자체가 없어 아예 동작하지 않았다.

**택하지 않은 안**
- *조회할 때 product_items를 조인/추가조회* — 페이지(40행)마다 왕복이 하나 더 생기고 옵션 수만큼 행이 딸려온다. 배송유형은 수집할 때만 바뀌는 값이라 매번 계산할 이유가 없다.
- *확장프로그램이 products에 대표 유형을 채우기* — 1단계(목록만) 수집처럼 배송 정보가 없는 업로드가 기존 값을 덮어써 지운다.

**택한 안** — `products.delivery_badges text[]`에 미리 접어두고, `product_items`의 statement 트리거가 갱신한다(004). 목록 조회는 추가 요청 0회, 필터는 GIN 배열 포함검색.

**섞여 있을 때** — 사용자 선택: 하나로 줄이지 않고 **옵션에 존재하는 유형을 전부 표시**. 예) 판매자배송 3개 + 판매자로켓 1개 → 두 배지 모두 표시. 순서는 `delivery_badge_rank()`로 로켓 계열 먼저.

**정규화** — 수집 라벨 표기가 제각각이라 5종으로 접되, 못 알아본 라벨은 판매자배송으로 몰지 않고 원문 그대로 남긴다("실제 옵션에 있는 값"이 화면에 보여야 하므로). `'판정불가'`는 정보 없음으로 보고 제외 → 배지가 하나도 없으면 `—`.

**같이 한 조회 최적화(기능 변경 없음)**
- 인덱스: `(max_sales desc) where is_active`, `(category_code, max_sales desc) where is_active`, 상품명 검색용 pg_trgm GIN. 상품명 검색은 그동안 인덱스가 없어 전체 스캔이었다.
- 옵션 펼치기: `product_items` → `user_items` 순차 2회를 `product_id`로 동시 요청 2회로 (user_items에도 product_id가 있고 `(user_id, product_id)` 인덱스가 이미 있다).
- 카테고리 필터 8000여 개 `<option>`을 createElement 루프 대신 문자열 한 번에 삽입, `full_path`는 정렬에만 쓰이므로 select에서 제외.
- 무한 스크롤 핸들러가 스크롤마다 `$('.main')`을 다시 찾던 것 캐시 + passive.
