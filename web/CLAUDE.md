# web/ — 웹사이트

## 구조
```
index.html   로그인 + 10개 페이지(소싱/판매현황/발주/입고/재고/출고/상품원장/즐겨찾기/카테고리/대기열) + 설정·SKU·청구서·출고 모달
style.css    CSS 변수 기반 라이트/다크 테마. --bg, --surface 등
app.js       전체 로직. 빌드 도구 없음, 그대로 배포
api/         Vercel 서버리스 함수 자리(현재 sales-today.js 하나, 안 씀 — 아래 참조)
package.json api/용 npm 의존성(undici) — 프론트엔드는 여전히 완전 무의존
```

Vercel에 **정적 파일 그대로** 올린다(플랫폼 확정, `../CLAUDE.md` 참조). 프레임워크·번들러 도입하지 말 것 — 사용자가 "복잡한 과정 없이"를 명시적으로 요구했다. `api/*.js`는 예외 — Vercel이 번들러 없이 그대로 서버리스 함수로 인식하는 기능이라 이 원칙과 안 부딪힌다.

**판매현황 탭은 다른 탭들과 데이터 소스·계산 시점이 완전히 다르다** — 소싱/즐겨찾기/카테고리는 웹이 실시간으로 계산하지만, 판매현황은 미리 쌓인 테이블을 읽기만 한다. `web/api/sales-today.js`는 그 이전 시도의 잔재로 지금은 아무것도 안 부른다 — 왜 이렇게 됐는지는 `../docs/decisions.md` 2026-08-13 항목.

**판매현황은 테이블이 세 개다(2026-08-15 추가) — 왜 안 합쳤는지 알아둘 것**:
- `rocket_growth_sales_daily`: 공식 Open API 기반, GCP VPS가 무인 cron으로 채움. 항상 최신이지만 **반품이 반영 안 됨**(`docs/api-notes.md` 4-4-1).
- `rocket_growth_sales_wing_daily`: WING 내부 API 기반(로그인 세션 필요), **반품이 순액으로 반영됨**(4-4-2), **옵션(vendorItemId)별**. 세션이 필요해서 무인 cron이 못 채우고, `extension/background.js`가 웹의 메시지 요청을 받아서 채운다.
- `rocket_growth_profit_daily`: 역시 WING 내부 API 기반(4-4-4), **수수료·입출고비·쿠폰·광고비·밀크런까지 전부 확정값**. 단 **계정 전체 합계**만 나오고 옵션별로 안 쪼개진다.

`rocket_growth_sales_daily`와 `rocket_growth_sales_wing_daily`는 **날짜 단위로** 병합한다(`fetchSalesRange()`) — 그 날짜에 wing 데이터가 하나라도 있으면 그 날짜는 wing만 쓰고 gross(Open API)는 통째로 무시, wing이 아예 없는 날짜만 gross로 폴백. 한 테이블로 합치지 않은 이유는 서로 다른 스크립트(무인 VPS cron vs. 사용자 브라우저의 확장프로그램)가 같은 컬럼에 동시에 쓰다가 경쟁하는 걸 피하기 위함(`db/CLAUDE.md`가 이미 이 원칙을 씀).

**왜 항목별이 아니라 날짜별로 병합하나(2026-08-16, 버그 수정)** — 처음엔 "(날짜,옵션) 단위로 wing 있으면 wing, 없으면 gross"로 병합했는데, **당일 매입+반품으로 순매출이 정확히 0이 된 옵션은 WING의 `sold-vendor-item-list` 목록 자체에서 빠진다**(0으로 찍히는 게 아니라 아예 없음 — `docs/api-notes.md` 4-4-2). 그래서 항목별 병합을 하면 이런 순제로 옵션이 gross의 반품 미반영 옛날 값 그대로 남아 매출이 과다 계상됐다(실측 사례: 2026-08-15에 12,900원 초과 계상, "일별 상세표 매출과 상품/옵션별 상세표 매출이 안 맞는다"는 사용자 지적으로 발견). WING이 그 날짜를 동기화했다면 그 목록 자체가 이미 완전한 진실이라 gross와 섞을 이유가 없어서, 날짜 단위로 통째로 택일하도록 바꿨다.

**판매현황 UI는 3단 구조다(2026-08-15 개편)** — 조회 기간 선택과 무관하게 항상 고정된 기간(이번 달/이번 주/최근 7일/오늘)을 보여주는 **상단 요약표**(`renderPeriodCards()`), 사용자가 고른 기간을 날짜별로 한 줄씩 보여주는 **일별 상세표**(`renderDailyTable()`), 그리고 그 기간의 옵션별 합산을 보여주는 기존 **상품/옵션별 상세표**(`renderSales()`) 순서다. 셋 다 `fetchAndRenderSales()`가 한 번 호출하는 `fetchSalesRange()`+`loadItemMeta()`의 결과 하나를 공유한다(옵션당 DB 조회를 중복하지 않기 위함) — 새 화면 요소를 추가할 때도 이 두 함수의 결과를 재사용할 것, 별도로 다시 조회하지 말 것.

**일별 한 줄(`buildDailyRow()`)의 필드별 출처가 다르다** — 이게 이 함수의 핵심이니 새로 건드릴 때 꼭 이해할 것:
- 수수료/입출고비/쿠폰비/밀크런/순이익/매출: 그 날짜에 `rocket_growth_profit_daily`(확정 정산) 행이 있으면 그 값 그대로, 없으면(주로 오늘 — 정산 인식 D-1 지연 추정) 옵션별 `commissionFor()`+`feeFor()` 추정을 그 날의 옵션별 판매에 적용해 합산한 값으로 대체한다. **확정/추정 여부를 화면에 별도로 표시하지 않는다** — 사용자가 명시적으로 "따로 추정치라고 표시할 필요 없다"고 요청함(2026-08-15).
- 원가/배송·작업비/영업이익: 정산현황 API 자체에 이 개념이 없어서(`docs/api-notes.md` 4-4-4) **항상** 옵션별 추정(`user_items.cost_cny` 등, `calcMargin()`)으로만 계산한다 — 그 날짜가 확정 정산이든 추정이든 상관없이 이 세 필드는 매번 옵션 단위로 다시 계산한다.
- 그날 판매된 옵션 중 원가가 하나도 입력 안 됐으면(`costedQty === 0`) 원가/배송·작업비/영업이익은 `null`("원가 입력 필요")로 표시 — 일부만 입력됐으면 입력된 만큼만 합산한다(기존 `renderSales()`의 "부분 계산 허용" 관례를 그대로 따름).

**상단 요약표의 "매출"은 항상 확정 쿠폰비를 뺀 값이다(사용자 요청)** — `sumDailyRows()`가 `revenue - coupon`을 계산해서 보여준다. 일별 상세표의 "매출" 칸은 쿠폰비를 빼지 않은 원래 값이고 "쿠폰비" 칸이 따로 있다 — 상단 요약과 하단 상세표에서 "매출"의 의미가 다르니 헷갈리지 말 것.

**`buildDailyRow()`는 오늘(KST) 날짜의 확정 정산(`confirmed`) 행은 내용과 무관하게 무조건 안 믿는다(`isToday` 체크, 2026-08-17, `docs/troubleshooting.md` #27·#29)** — 두 단계로 발견된 문제다.

1차(#27, 2026-08-16): WING `profit-status/search`가 그 날짜를 아직 인식 안 했을 때도 HTTP 200 + `profitAmount:0`인 "필드는 다 있지만 전부 0" 응답을 줄 수 있는데, 예전엔 `syncProfitForDates()`가 이걸 성공으로 오인해 그대로 저장했었다. `confirmed.total_sales_amount`/`total_deduction_amount`가 **둘 다 0이면서 그날 실제 판매수량(quantity)이 있으면** 확정으로 안 믿는 `looksEmpty` 체크로 1차 방어함.

2차(#29, 2026-08-17): 그런데 이 휴리스틱으로도 못 잡는 사례가 실사용 중 나왔다 — 오늘 실제 판매 0건인데 `profit-status`가 `fulfillment_amount:6470`, `storage_amount:1282`(**0이 아님**, `looksEmpty` 통과)를 줘서 순이익 −6,470원이 "확정"으로 화면에 떴다. 보관비 같은 항목은 판매 이벤트 없이도 창고 재고 기준으로 매일 누적되는 비용이라 부분적으로 먼저 채워질 수 있는 것으로 보인다 — **"필드가 0이 아니다"가 "그날 정산이 최종 확정됐다"를 보장하지 않는다.** 사용자가 WING 정산현황 페이지에서 "오늘 날짜 자체가 원래 안 나온다(항상 D-1까지만)"고 확인해줘서, "전부 0인지" 휴리스틱 대신 **`date === kstDateStr(new Date())`(오늘이면 무조건)** 규칙으로 바꿨다 — WING 자신의 D-1 표시 경계와 원칙을 맞춘 것이라 더 단순하고 확실하다. `looksEmpty` 체크는 오늘이 아닌 날짜(예: 정산 백필한 과거 날짜)에 비슷한 빈 행이 생기는 경우까지 방어하려고 그대로 남겨둠 — 두 조건 다 `hasConfirmed` 계산에 들어감.

`fetchSalesRange()`의 select에 `total_sales_amount`/`total_deduction_amount` 컬럼이 있어야 `looksEmpty` 체크가 동작한다 — 지우지 말 것. 확장프로그램(`extension/background.js`)도 완전히 빈(전부 0) 응답은 저장 안 하도록 고쳤지만(근본 방어 중 하나), 오늘 날짜의 "부분적으로 채워진" 응답까지는 확장프로그램 단에서 걸러낼 뾰족한 기준이 없어서 — **웹의 `isToday` 체크가 최종 방어선**이다.

**일별 상세표는 날짜가 2개 이상이면 맨 위에 "합계" 행을 고정 표시한다(사용자 요청, 2026-08-16)** — `renderDailyTable()`이 `sumDailyFullRows()`로 조회 기간 전체를 합산해서 날짜별 행들 위에 얹는다. 날짜 정렬(최신이 위)과 무관하게 합계는 항상 맨 위 고정. `sumDailyRows()`(상단 고정기간 카드용, 매출/순이익/영업이익 3개 필드만 반환)와는 별개 함수 — 일별 상세표는 칸이 더 많아서(수수료·입출고비·보관비 등) 재사용하지 않고 `sumDailyFullRows()`를 새로 뒀다. cost/shipWork/operatingProfit은 원가 입력된 날짜만 골라 합산(기존 "부분 계산 허용" 관례 그대로).

**상품/옵션별 상세표는 이제 날짜별 그룹핑 구조라 "판매일수" 컬럼 자체가 없어졌다** — 2026-08-16 저녁 개편으로 각 행이 이미 "그 날짜의 그 옵션" 하나씩이라 별도 날짜 컬럼이 불필요해짐. 이 항목(예전엔 `dayDetailCell()`/`<details>` 방식)은 완전히 대체됐으니 되살리지 말 것 — 지금 구조는 위 "상품/옵션별 상세표 구조" 항목 참조.

**대조(reconciliation) 안내(`renderReconcileNote()`, 2026-08-15 신설 → 2026-08-17 확장)** — 정산현황 API는 계정 전체 합계만 주고 어떤 상품이 팔렸는지가 없어서, 상품별 합산과 정산현황은 서로 다른 API에서 각각 나온 값이라 구조적으로 100% 일치할 보장이 없다. 조회 기간 안에 확정 정산이 있는 날짜만 골라 **매출·수수료+입출고비·순이익 세 가지 모두**(2026-08-17 전엔 매출만 비교했음)를 대조해서 차이가 나면 보여준다.

**2026-08-17에 이 차이의 원인을 실측 대조로 규명했다**(`docs/decisions.md` 2026-08-17 항목에 조사 경위 전체) — 두 가지:
1. **수수료 부가세 차이(해결됨)**: 상품별 원가 스냅샷(`commission_amount`/`fulfillment_amount`)은 WING 재고현황 "예상(개당)" 값으로 부가세 별도인데, 확정 정산 필드(`totalTakeRateAmountWithVat` 등)는 이름 그대로 부가세 포함이다. `withSnapshotVat()`(×1.1)로 스냅샷 기반 수수료·입출고비 계산에 보정을 넣어서 수수료 쪽은 이제 정확히 일치한다(8/16 실측 확인). **카테고리 요율 폴백(`commissionFor()`/`feeFor()`)에는 이 보정을 안 넣는다** — 그쪽은 부가세 포함 여부를 검증한 적이 없어서, 근거 없이 씌우면 새 오차를 만들 수 있다. 쿠폰비도 보정 대상 아님(보정 없이 이미 정확히 일치).
2. **반품처리비 미귀속(구조적 한계로 확정, 부분 완화만 가능)**: 당일 매입+당일 반품으로 순수량이 정확히 0이 된 옵션은 WING `sold-vendor-item-list`에서 아예 빠진다(0으로 안 찍히고 없음, `docs/troubleshooting.md` #26과 같은 원인). 그 옵션의 반품처리비가 확정 정산(계정 전체 합계)엔 들어있지만 상품별 집계엔 애초에 계산 대상이 안 돼서 빠진다. **이걸 상품별로 정확히 귀속시킬 방법을 조사했으나 불가능으로 결론남(2026-08-17)** — 로켓그로스는 CS·반품을 쿠팡이 전담하는 구조라 마켓플레이스 셀러와 달리 개별 반품 건을 보여주는 화면이 WING에 아예 없다(사용자 확인, 실제 API 캡처 90건에도 반품 관련 엔드포인트 전무 — `docs/decisions.md` 2026-08-17 항목). **안분 배분도 검토했으나 채택 안 함**(관련 없는 다른 옵션에 비용을 억지로 배정하는 가짜 정밀도라 AI 분석 지향 원칙에 안 맞음) — 대신 이 대조 안내로 차액을 투명하게 보여주는 쪽으로 마무리. **앞으로 이 문제를 또 "해결해볼까" 하는 생각이 들면 이 항목부터 먼저 읽을 것** — 이미 막다른 길로 확인된 방향이다.

`buildDailyRow()`의 리턴 객체에 `itemFeeCombined`/`itemNetProfit`(hasConfirmed 여부와 무관한 옵션별 추정 원값)을 `itemRevenue`와 같은 방식으로 추가해서 이 대조가 가능해졌다 — 새 대조 항목을 늘리려면 이 패턴을 그대로 따를 것(확정/추정 두 값을 각각 보존해야 대조 가능).

**옛 카드(`salesProfitCard`/`renderProfitSummary()`, `salesStats`)는 위 3단 구조로 완전히 대체되어 삭제됨(2026-08-15)** — 코드나 커밋 히스토리에서 이 이름을 보면 이미 없어진 것이니 되살리지 말 것.

**"확정"된 날짜도 값이 계속 바뀐다 — 캐시가 낡았다고 놀라지 말 것(2026-08-15 실측 확인)**. WING의 정산 인식은 D-1 지연뿐 아니라 그 이후로도 며칠에 걸쳐 거래가 하나씩 더 인식되면서 같은 날짜의 `profit_amount` 등이 계속 갱신되는 것으로 보인다(실제로 08-15 하루치가 몇 시간 사이 47,719원 → 58,293원으로 바뀐 걸 확인함). 그래서 "몇 시간 전 스크린샷과 지금 화면이 다르다"는 건 버그가 아니라 정상 — 비교할 땐 항상 WING 위젯도 같은 시점에 새로고침해서 볼 것. 오늘·어제는 탭 열 때마다 자동 재동기화되니 최신을 유지하지만, 그보다 과거 날짜가 계속 바뀌는 게 걱정되면 정산 백필을 다시 눌러서 갱신하면 된다(단, 완전히 확정된 뒤엔 거의 안 바뀌는 것으로 보임 — 확실친 않음, 더 지켜볼 것).

**보관비(`storage_amount`, `db/migrations/011`, 2026-08-15 추가) — 새 API 호출 없이 이미 받던 필드를 분리한 것.** `profit-status/search` 응답의 `profitStatusDeductionDetail.totalStorageFeeAmount`는 010부터 이미 매번 받아왔지만 `fulfillment_amount`(=totalCfsAmountWithVat, 배송비+입출고비+보관비+부가세 합계 — 2026-08-17에 WING "수익 현황" 화면 스크린샷으로 정확한 4개 구성요소를 확인함, 아래 "부가세" 항목 참조)에 묶여서 안 보였다 — 일별 상세표에 참고용 별도 컬럼으로만 추가했다. **`fulfillment_amount`에 이미 포함된 금액이라 두 컬럼을 더하면 이중 계산.** 확정 없는 날(추정)은 옵션별 추정 합계를 대신 쓴다(2026-08-17부터, 예전엔 0이었음 — 아래 "buildDailyRow() 추정 로직" 참조).

**부가세(`vat`, 일별·상품/옵션별 둘 다 2026-08-17 추가) — WING 자신의 "수익 현황" 화면(사용자 스크린샷)에서 근거를 찾았다.** 그 화면의 "풀필먼트서비스 비용" 항목이 배송비+입출고비+보관비+부가가치세 네 줄로 쪼개져 있고, 툴팁에 "부가가치세는 조회된 기간에 발생한 요금의 10%로 계산"된다고 명시돼 있다 — 실측 검산(9,336원)까지 정확히 일치해서 공식을 확정했다: **부가세 = ROUND((입출고비 + 보관비) × 0.1)**.
- **일별 상세표(확정일)**: WING이 `fulfillment_amount` 하나만 주고 이 네 구성요소를 안 쪼개주므로, 수학적으로 `fulfillment_amount ÷ 11`이 "그 안에 이미 포함된 부가세"와 완전히 같다(총액=세전×1.1이므로 세전=총액÷1.1, 부가세=총액−세전=총액÷11 — `storage_amount`가 이미 `fulfillment_amount`의 서브셋이라 굳이 따로 더할 필요도 없음). 그래서 확정일은 `Math.round(confirmed.fulfillment_amount / 11)`로 계산한다. **표시용 참고 컬럼이라 기존 "입출고비" 값·`netProfit` 계산엔 전혀 영향 없다** — WING의 `profit_amount`가 이미 부가세를 포함한 진짜 확정값이라 그대로 씀.
- **일별 상세표(추정일, 아래 "buildDailyRow() 추정 로직" 참조)**: `Math.round((estFulfillment + estStorage) * 0.1)`로 직접 계산하고, 이 값을 실제로 `estNetProfit` 계산에서 뺀다(추정치는 WING이 미리 다 계산해주는 확정치와 달리 우리가 직접 6개 항목을 다 빼야 함 — 아래 순이익 공식 참조).
- **상품/옵션별 상세표**: 이 표는 애초에 옵션별 보관비를 안 다루므로(아래 "보관비는 이제 옵션 단위가 아니다" 항목), 옵션 행은 그 옵션의 입출고비(세전)만 기준으로 `Math.round(fulfillment * 0.1)`을 계산하고, 날짜 합계 행에서 옵션별 부가세 합 + 그 날짜 고정 보관비의 10%를 추가로 더해서 진짜 WING 공식(입출고비+보관비 합의 10%)을 완성한다.

**순이익 공식이 부가세를 포함하도록 확장됨(2026-08-17, 사용자 확정)** — **순이익 = 매출 − 수수료 − 입출고비 − 보관비 − 쿠폰비 − 광고비 − 부가세**. 확정일은 WING의 `profit_amount`가 이미 이 전부를 반영한 진짜 값이라 그대로 쓰고, 추정일만 이 여섯 항목(광고비는 추정 방법이 없어 항상 0)을 직접 뺀다.

**상품/옵션별 상세표는 WING 실제 개당 원가정보를 우선 쓴다(2026-08-16 구현, 2026-08-17 계산식 일부 수정)** — 카테고리 요율표 추정(`commissionFor()`/`feeFor()`)보다 `rocket_growth_item_cost_snapshots`(`db/migrations/012`, "상품 원가정보 갱신" 버튼으로 채움)의 실제값을 우선 쓴다. **수수료는 스냅샷 값에 `withSnapshotVat()`(×1.1)을 곱해서 쓴다** — WING 재고현황 "예상(개당)" 값이 부가세 별도라서(2026-08-17 실측 검증: ×1.1이 확정 수수료와 정확히 일치). **입출고비는 반대로 스냅샷 원값(세전) 그대로 쓴다** — 부가세를 여기서 바로 곱하면(예전엔 그랬었음) 위 "부가세" 항목에서 설명한 (입출고비+보관비) 합산 기준 부가세 계산과 안 맞아서, 2026-08-17에 되돌렸다. 정말 스냅샷이 하나도 없는 상품만 카테고리 추정으로 폴백, 폴백된 항목만 "(추정)" 표시.

**표는 "범위 전체를 한 번에 합산"이 아니라 날짜별로 따로 계산해서 더한다(`renderSales()`)** — 같은 상품이라도 판매된 날짜에 따라 적용해야 할 원가 스냅샷이 다를 수 있어서다(가격이 바뀌면 스냅샷도 새로 쌓이므로). 그날 판매의 평균단가 대비 그 시점 스냅샷의 개당 수수료 비율을 환산해 `calcMargin()`에 넣는 방식이라(반올림 없이 원래 금액으로 정확히 되돌아오는 산술이라 근사치 아님) 별도 계산식을 새로 만든 게 아니라 `calcMargin()`을 그대로 재사용한다.

**`snapshotAsOf(snapshots, dateStr)`는 두 단계로 고른다** — 1순위 "그 날짜 이전 중 가장 최근 스냅샷"(`exact:true`, 진짜 그 시점 요율). 그게 없으면(스냅샷을 도입하기 전에 팔린 과거 판매 — 처음 "상품 원가정보 갱신"을 누르기 전 날짜들) **2순위로 그 상품에 있는 것 중 가장 이른(=시간상 가장 가까운) 스냅샷을 참고값으로 대신 쓴다**(`exact:false`, 화면엔 "(참고용)"으로 표시) — 사용자가 "과거 데이터도 빈칸보다 값이 있어야 정산현황과 맞는지 검증하기 편하다"고 명시적으로 요청해서 추가함(2026-08-16). **이 참고용 값은 그 날짜의 진짜 요율이 아닐 수 있다** — 스냅샷을 도입한 이후 시점의 요율을 과거에 그대로 끌어다 쓴 것뿐이니, 검증·참고 용도로만 쓸 것. 오프셋이 다른 ISO 문자열(DB는 UTC, 계산은 KST)을 문자열로 비교하면 순서가 깨지니 **반드시 `Date` 객체의 epoch ms로 비교할 것** — 이미 그렇게 짜여 있음, 문자열 비교로 "최적화"하지 말 것.

**`loadItemCostSnapshots(vendorItemIds)`는 날짜로 필터링하지 않고 그 상품의 스냅샷을 전부 가져온다(2026-08-16, 버그 수정)** — 처음엔 `captured_at <= 조회기간 끝`으로 걸러서 가져왔는데, 이러면 스냅샷이 전부 조회기간보다 나중에 찍혔을 때(예: 오늘 막 처음 "상품 원가정보 갱신"을 눌렀는데 "어제"만 조회) **SQL 단계에서 스냅샷이 통째로 걸러져서 `snapshotAsOf()`의 2순위 폴백(참고용)까지 같이 막혀버리는 버그**가 있었다(실사용 중 "갱신해도 여전히 정보 없음"으로 발견). `snapshotAsOf()` 자체가 이미 "그 날짜 이전 것 우선, 없으면 가장 이른 것"을 알아서 골라내므로, 여기서 미리 날짜로 좁힐 필요가 없다 — **앞으로 이 함수에 필터를 다시 추가하고 싶어지면, 그게 `snapshotAsOf()`의 참고용 폴백을 못 쓰게 막는 건 아닌지부터 확인할 것.**

**보관비는 이제 옵션 단위가 아니다 — "고정 보관비"로 날짜 단위에서만 다룬다(2026-08-17, 설계 변경)** — 처음엔(2026-08-16) 옵션별로 `storageAllocationForItem()`(그 옵션의 이번달 누적보관비 ÷ 경과일수)을 배분해서 보여줬는데, 사용자가 "보관비는 그날 팔린 특정 주문에 안 묶이는 재고 전체 기준 고정비"라고 지적 — 특정 옵션에 배분하는 게 오히려 억지 정밀도였다. 그래서:

**`.table-wrap`이 `overflow:hidden`에서 `overflow-x:auto`로 바뀜(2026-08-16)** — 컬럼이 많은 표(특히 일별 상세표, 13칸)가 좁은 화면에서 브라우저 기본 동작으로 상품명 칸이 무한정 압착되던 문제의 근본 원인. 가로 스크롤이 생기게 해서 압착 대신 스크롤로 처리되게 함. `overflow-y: hidden`은 유지했으므로 `thead`의 `position:sticky` 기준(가장 가까운 non-visible-overflow 조상)은 그대로 `.table-wrap`이라 세로 스티키 동작엔 영향 없음(가로/세로 overflow 값이 다르면 브라우저가 둘 다 non-visible로 강제 승격하는 스펙 때문에 원래도 `.table-wrap`이 스티키 기준이었음 — 이번 변경으로 새로 생긴 동작 아님).

**판매현황 페이지 상단의 계산 방식 설명 hint-box는 화면에서 뺐다(사용자 요청, 2026-08-16 — 공간을 너무 차지한다는 피드백)** — 예전에 `index.html`의 `#page-sales` 맨 위에 있던 안내문 원문을 유실 없이 여기 남겨둔다. 이 문서(위 여러 항목)와 내용이 겹치지만, **화면에 다시 노출할 일이 생기면 아래 원문을 그대로 복원하면 된다**(재작성하지 말 것 — 사용자가 검증했던 정확한 문구):

> 확정 정산(WING)이 있는 날짜는 수수료·입출고비·쿠폰비·밀크런·순이익을 그대로 쓰고, 없는 날짜(주로 오늘 — 정산 인식이 하루 지연됨)는 카테고리 실제 요율+요금표로 추정합니다. 원가·배송/작업비·영업이익은 정산현황 API 자체에 없는 값이라 항상 옵션별 추정입니다 (사이즈·원가 미입력 옵션은 이익 합계에서 빠집니다). 일별 상세표의 보관비는 입출고비 안에 이미 포함된 금액을 참고용으로 따로 보여주는 것이라 두 컬럼을 더하면 중복 계산됩니다. 상품/옵션별 상세표의 수수료·입출고비·쿠폰비는 "상품 원가정보 갱신"으로 가져온 WING 실제 개당 값을 우선 씁니다(쿠폰비 = 재고현황의 즉시할인+다운로드쿠폰 합계, 확정 정산의 쿠폰비 항목과 같은 계산 방식으로 맞춘 것 — 실제 WING 화면의 "최종구매가" 기준과 다르면 알려주세요). 판매 시점 이전에 찍힌 스냅샷이 없으면(과거 판매인데 아직 갱신을 안 해봤을 때) 있는 것 중 가장 가까운 스냅샷을 대신 써서 "(참고용)"으로 표시합니다 — 그 날짜의 진짜 요율이 아닐 수 있어 검증·참고용입니다. 스냅샷 자체가 하나도 없는 상품만 카테고리 추정으로 폴백하고 "(추정)"으로 표시합니다(카테고리 추정엔 쿠폰비 개념이 없어 이 경우 쿠폰비는 0으로 계산됩니다). 이 표의 보관비는 입출고비와 별개(중복 아님)이고 이번 달 누적치를 조회 기간만큼 배분한 참고값이라 순이익에는 반영하되 영업이익 계산에는 넣지 않습니다.

**이날(2026-08-16) `buildDailyRow()`가 카테고리 추정에서 상품 원가정보 스냅샷 우선으로 바뀌었으니, 위 원문의 "없는 날짜는 카테고리 실제 요율+요금표로 추정합니다" 문장은 이제 부정확하다** — 복원할 때는 "카테고리 실제 요율+요금표로 추정" 부분을 "상품 원가정보 스냅샷(없으면 카테고리 요율)으로 추정"으로 고쳐서 쓸 것. 아래 새 항목 참조.

**`buildDailyRow()`도 상품 원가정보 스냅샷을 우선 쓰도록 바뀜(2026-08-16, `docs/troubleshooting.md` #27 후속)** — 처음 #27을 고쳤을 때는 "빈 확정 행을 안 믿고 추정으로 폴백"까지만 했는데, 그 추정 자체가 여전히 카테고리 요율(`commissionFor()`/`feeFor()`)만 쓰고 있어서, 카테고리 매칭이 안 된 계정은 당일 매출·판매수량만 뜨고 수수료·입출고비·보관비·쿠폰비·순이익은 계속 0으로 보이는 문제가 남아 있었다(광고비·밀크런은 정산현황 API 전용값이라 추정 방법이 원래 없음 — 사용자가 이건 당일엔 0이어도 된다고 확인함). `renderSales()`가 이미 하던 것과 동일하게 `snapshotAsOf()`로 상품별 실제 개당 원가를 먼저 찾고, 없는 상품만 카테고리 요율로 폴백하도록 통일했다. 보관비도 `storageAllocationForItem(snapshots, 1)`로 "그날 하루치" 배분을 새로 추정한다(기존 함수는 이미 임의 일수를 받게 설계돼 있어 `rangeDayCount=1`만 넘기면 그대로 재사용 가능했음). **`fetchAndRenderSales()`가 이제 `loadItemCostSnapshots()`를 조회 범위 전체(`fetchFrom~fetchTo`, 상단 고정기간 카드까지 커버하는 넓은 범위)로 한 번만 호출해서 `buildDailyRow()`와 `renderSales()`가 같이 재사용한다** — 예전엔 `renderSales()`가 선택 기간(`fromDate~toDate`)만큼만 따로 불러왔는데, 이제 그 범위는 항상 fetchFrom~fetchTo의 부분집합이라 중복 조회 없이 그대로 재사용 가능. 새 화면 요소가 원가 스냅샷이 필요하면 이 공유 `costSnapshots`를 재사용할 것, 별도로 다시 조회하지 말 것(기존 "두 함수 결과 공유" 관례의 연장).

**`loadSales()`가 `syncSalesViaExtension()`을 매번 호출한다** — `chrome.runtime.sendMessage(SALES_EXT_ID, ...)`로 브라우저 확장프로그램(설치돼 있고 WING에 로그인돼 있다면)에게 "오늘+어제" 반품 데이터를 다시 동기화해달라고 요청한다. 확장프로그램이 없거나 응답이 없어도(일반 방문자, 다른 브라우저 등) 타임아웃 후 조용히 기존 방식으로 넘어간다 — **이 호출이 실패해도 판매현황 자체는 항상 정상 동작해야 한다**, 이 전제를 깨는 수정을 하지 말 것. `SALES_EXT_ID`는 확장프로그램의 크롬 ID(`chrome://extensions`에서 확인)라서 확장프로그램을 다른 폴더로 옮기거나 웹스토어에 정식 배포하면 바뀔 수 있음 — 그러면 이 상수도 같이 갱신해야 함.

## 절대 바꾸지 말 것

1. **`user_items`/`item_calc`에 쓸 때 `on_conflict=user_id,item_id`를 빼지 말 것.** 빼면 사용자 간 데이터가 서로 덮어써진다 (RLS는 읽기만 막지, upsert 충돌 키는 별개).

2. **마진 계산은 `calcMargin()` 하나로 통일할 것.** 다른 곳에서 직접 계산식을 새로 쓰지 말고 이 함수를 재사용. 실제 청구서로 검증된 값(2,538원)과 어긋나면 잘못된 것.

3. **`recalcRow()`의 자동저장에 디바운스(`debounce`, 600ms)가 걸려 있다.** 제거하면 타이핑마다 API 호출이 나가 느려진다.

## 알아야 계산 가능한 것

```javascript
calcMargin({price, commission, fulfillment, costCny, rate, outbound, work})
// commission이 null이면 통째로 null 반환(계산 자체를 안 함) — "수수료 정보 없음"
// costCny가 null이면 margin/rate/shipWork는 null, settlement까지는 반환됨 — "원가 입력 필요"
// 이 둘은 화면에서 서로 다른 문구로 구분해서 보여준다. 섞어서 하나로 뭉치지 말 것.
// shipWork(=outbound+work, 2026-08-15 추가)는 판매현황 일별표의 "배송·작업비" 칸을 위해
// margin과 별도로 빼둔 것 — margin 자체가 이미 이 값을 뺀 결과라 이중 계산 아님.
```

**전역 기본 수수료율은 없다(2026-08-13 이후).** `commission`은 항상 `commissionFor(catCode)`(카테고리별 실제 요율, `state.catUnits[catCode].commission`)로 구해서 넘긴다 — `settings.commission` 같은 전역 폴백은 의도적으로 없앴다. 매칭 안 된 카테고리는 `commissionFor()`가 null을 반환하니, 호출부에서 `calcMargin()`을 부르기 전에 먼저 null 체크하고 "수수료 정보 없음"을 보여줄 것(소싱 옵션표/판매현황 표의 기존 4개 호출부가 이 패턴이다 — 새로 만들 때 그대로 따라할 것).

입출고비는 `feeFor(catCode, size, price)`가 `state.feeCache`(메모리 캐시, `loadFeeTables()`가 앱 시작 시 전체 로드)에서 구간 조회한다. **DB를 매번 조회하지 않는다** — 요금표가 수천 행이라 캐시가 필수.

**`state.readyForMargins`에 새 비동기 로딩을 추가할 때 반드시 챙길 것** — 이 프로미스는 "마진 계산에 필요한 모든 상태가 준비됐다"는 신호다(`enterApp()`에서 `Promise.all([loadSettings(), loadFeeTables(), loadCategoryOptions()])`). 마진 계산이 참조하는 `state`의 어떤 부분이든(예: `state.catUnits`) 새로 채우는 로딩 함수를 추가하면 **여기에도 같이 넣어야 한다** — 안 그러면 "카테고리 로딩이 끝나기 전에 사용자가 너무 빨리 클릭"하는 경쟁 상태가 생기고, 소싱 목록(`loadRowMargins`)과 옵션 펼치기(`loadOptions`) 둘 다 이 프로미스만 기다리고 결과를 **한 번 캐시하면 다시 재계산 안 하므로** 잘못된 "정보 없음" 상태가 영구히 굳어버린다. 실제로 2026-08-13에 `loadCategoryOptions()`가 빠져서 이 버그가 두 군데서 났었다.

## 상품원장 탭 (2026-08-18 신설)

**이 화면은 목록을 만들지 않는다.** `my_skus`는 `scripts/rocket-growth-sync.js --skus`가
쿠팡 Open API에서 바코드까지 자동 적재한다(GCP VPS). 화면이 하는 일은
**쿠팡이 줄 수 없는 것만 사람이 채우는 것**이다 — 1688 링크·옵션(중국어)·MOQ·리드타임·한글표시사항.
그래서 "SKU 추가" 버튼이 없다. 이건 빠뜨린 게 아니라 의도다(손으로 만든 SKU는
바코드가 없어서 발주·청구서와 이어지지 않는다).

**쿠팡에서 온 값은 모달에서 읽기전용**(`#skuRo`) — 바코드·옵션ID·등록상품ID·등록상품명.
고쳐봐야 다음 동기화에 덮이거나 조인이 깨진다.

**조인을 클라이언트에서 하는 이유**: `my_skus` + `my_products` + `sku_channel_listings` +
`sku_suppliers` 네 테이블을 각각 통째로 받아 JS에서 합친다. SKU 수천 개까지 가도 몇백 KB라
PostgREST 중첩 조인보다 단순하고 빠르다 — 소싱 탭이 8000행을 같은 방식으로 다루고 있어 관례도 일치.

**`sku_channel_listings`를 거치는 이유**: `my_skus`에 쿠팡 옵션ID를 직접 안 박았다(채널 독립 구조,
`db/migrations/015` 주석). 지금은 `channel === 'coupang_rg'`만 쓰지만, 나중에 스마트스토어가
붙어도 이 화면은 안 고쳐도 된다.

**MOQ를 사람이 고치면 `moq_source`가 `'manual'`로 바뀐다** — 나중에 쿠플러스에서 1688 MOQ를
자동으로 긁어올 때 사람이 정한 값을 덮어쓰지 않기 위한 표시다. 이 갱신을 지우지 말 것.

**공급처는 SKU당 여러 개 가능**(`sku_suppliers`, 같은 상품을 여러 1688 판매자에게서 살 수 있음).
이 화면은 `is_primary` 하나만 편집한다 — 복수 공급처 비교는 나중에 공급처 관리 화면에서.

## 발주 탭 + 청구서 인식 (2026-08-18 신설)

**원가가 태어나는 화면.** 청구서 하나를 인식해서 `purchase_orders` + `purchase_order_lines` +
`inventory_lots` 세 테이블을 한 번에 만든다.

**역할 분리 — 왜 PDF 해석만 서버에 있나**
```
web/api/parse-invoice.js   PDF 바이트 -> 텍스트   (pdf-parse, 이것만 함)
web/app.js parseCouplusInvoice()   텍스트 -> 줄 구조  (파싱 규칙 전부 여기)
```
파싱 규칙은 자주 손보게 되는데 브라우저 쪽이면 배포 없이 바로 확인된다. 그리고 사용자가
텍스트를 직접 붙여넣는 경로("PDF 인식이 안 되면")와 로직을 한 벌로 공유한다.
서버 함수는 라이브러리가 필요한 부분만 맡는다 — 외부 네트워크 호출이 없어서
`sales-today.js`의 고정 IP 문제와도 무관하다.

**`parseCouplusInvoice()`가 서 있는 함정들** (자세한 근거는 `docs/decisions.md` 2026-08-18)
- 줄이 **1688 주문 묶음**으로 그룹져 있는데, **배송비·총금액이 어느 줄에 찍히는지가 매번 다르다**
  (첫 줄 / 한가운데 줄 / 아예 독립된 줄 — 세 형태를 다 겪었다). 그래서 위치로 안 풀고
  **산수로 푼다**: 위에서부터 (수량 x 단가)를 누적하다 다음 총금액과 맞는 순간 끊는다.
  맞아떨어지는 것 자체가 검산이다.
- **줄 단위로 읽되, 날짜로 시작하지 않는 줄을 둘로 나눈다**: 직전 상품 줄이 안 끝났으면
  그 줄의 이어짐, 끝났으면 묶음 값만 따로 그려진 줄. "끝났는지"는 바코드 칸(숫자가 아닌
  토큰)이 나왔는지로 본다. 첫 날짜 이전 줄은 통째로 무시한다(계좌번호의 긴 숫자 오인 방지).
- 상품명에 "3p" 같은 토큰이 섞여도 **순수 숫자만** 세므로 안전하다.
- **바코드 칸은 공백이 든 자유 텍스트일 수 있다**(실제로 "핑크 호빵 스퀴지"가 온 적 있음) —
  토큰 하나가 아니라 뒤쪽 비숫자 구간 전체를 뗀다.
- **협상후 단가는 총액에서 역산된 소수점 5자리**라 계산에 쓰지 않는다(표시용).
  계산 기준은 언제나 묶음 총금액이고, 그룹 합계와 대조해 `diffCny`로 검산한다.
- **환율은 청구서에 안 적혀 있다** → 전체 KRW ÷ 전체 CNY로 역산하고 화면에 근거를 보여준다.

**실측 검증(2026-08-18)**: 2026-06-26 청구서 전문으로 25줄·13묶음 인식, 묶음 검산 불일치 0건,
역산 환율 정확히 320.00, 역검증 2055.28 CNY × 320 = 657,690원 = 청구서 기재 금액과 일치.

**저장 전 사람 확인은 건너뛸 수 없다** — 인식이 틀린 채 저장되면 원가가 조용히 어긋나고,
원가는 이익 계산의 바닥이라 뒤늦게 발견하기 가장 어렵다. 확인 화면에서 미매칭 줄 수와
묶음 검산 차액을 경고로 띄운다.

**바코드가 매칭된 줄만 로트를 만든다** — SKU를 모르는 원가는 어디에도 못 붙는다.
줄(`purchase_order_lines`)은 그대로 남기므로, 나중에 상품원장에서 바코드가 채워지면
그때 로트를 만들 수 있다.

**PDF 텍스트 추출은 좌표 기반이다(2026-08-18)** — `pdf-parse` 기본 추출기가 칸 사이 공백을
버려서 파서가 통째로 오작동한 적이 있다(`docs/troubleshooting.md`). `pagerender` 훅으로
직접 구현했고, 실패 시 기본 추출로 폴백한다. 확인 화면의 **"인식된 원문 보기"**와
**숫자 구조 경고**(줄당 숫자 7·3·1개, 수량은 양의 정수)가 이 종류의 사고를 다시 조용히
넘어가지 않게 하는 장치다 — 지우지 말 것.

**이 청구서는 같은 업체가 발행해도 줄 구조가 매번 다르다(2026-08-18, 세 번 연속으로 겪음).**
구조를 가정하지 말고 **검산과 경고**에 기댈 것 — 새 형태가 또 나올 것을 전제로 짜여 있다.
검증된 형식 5종은 `docs/decisions.md` 2026-08-18 표 참조.

## 발주 상세 — 청구서 줄에 SKU 수동 연결 (2026-08-18 신설)

발주 목록에서 행을 누르면 열린다. **바코드가 없거나 못 찾은 줄에 사람이 SKU를 붙이는 화면**이다
(과거 청구서는 전부 `NOBARCODE`라 자동 매칭이 안 된다). 사용자는 앞으로 대부분 바코드를
넣고 발주하지만 안 넣는 경우도 있다고 확인해줘서(2026-08-18), 이 화면은 계속 필요하다.

**로트는 SKU가 붙는 순간 만들어진다.** 청구서 저장 시엔 매칭된 줄만 로트를 만들었으므로,
여기서 뒤늦게 붙인 줄도 같은 규칙으로 로트를 만들어야 선입선출 대기열에 들어간다.
**이미 로트가 있는 줄은 연결 해제 버튼 자체를 안 보여준다** — 바꾸면 로트가 붕 떠서
재고·원가가 어긋난다. `cost_breakdown.linked_manually`로 사람이 붙인 연결임을 남긴다.

**상품명 추천은 글자 2개씩 겹치는 비율(Dice 계수)로 계산한다**(`suggestSkus()`).
한글은 단어 단위로 비교하면 잘 안 맞는다 — "도시락 말랑이" vs
"덴넬 도시락 말랑이 슬라임 스퀴시, 노랑 100g 2개"처럼 청구서명이 훨씬 짧기 때문이다.
실측(2026-08-18): 정답 SKU가 있으면 항상 1순위로 올라온다(38~82%). 정답이 없으면
엉뚱한 게 29% 정도로 뜨므로 **자동 적용하지 말 것** — 후보 제시까지만 하고 판단은 사람이 한다.

**후보 목록은 `<select>`가 아니라 `<datalist>`다** — SKU가 수천 개가 돼도 브라우저가 알아서
걸러준다. select였다면 option 수천 개를 그리느라 느려진다.

**`POD.picks`의 키는 항상 문자열로 맞출 것** — DOM `dataset`에서 오는 값은 문자열이고
`purchase_order_lines.id`는 숫자라, `String()`으로 안 맞추면 고른 값이 **조용히 무시된다**
(2026-08-18에 실제로 겪음 — 칩을 눌러도 아무 일도 안 일어나는 것처럼 보였다).

**바코드 칸도 발주 상세에서 고칠 수 있다(2026-08-18, 사용자 요청)** — 쿠플러스에 바코드를
안 넣고 발주한 건은 여기서 나중에 채워 넣는 게 가장 자연스럽다. 고치면 **먼저 그 바코드의
SKU가 있는지 보고**, 있으면 자동 연결, 없으면 연결을 비워서 원래처럼 검색·추천이 뜬다.
**이미 로트가 만들어진 줄은 바코드 글자만 바뀌고 SKU 연결은 안 건드린다** — 로트가 붕 뜨기 때문.
청구서 원문은 `purchase_order_lines.raw_line`(jsonb)에 그대로 남으므로 이 칸을 고쳐도
원본을 잃지 않는다. 연결과 바코드는 한 줄에 둘 다 바뀌었으면 PATCH 한 번으로 함께 저장한다.

**SKU를 고르면 바코드 칸도 그 SKU의 바코드로 맞춘다(`podPick()`, 2026-08-18 사용자 요청)** —
둘이 다른 채로 저장되면 나중에 "이 줄이 왜 이 상품에 붙었지"를 추적할 수 없다.
SKU에 바코드가 없으면 기존 값을 **지우지 않는다** — 있는 정보를 없애는 쪽이 더 나쁘다.

**발주 목록의 "로트" 칸이 저장이 제대로 됐는지 확인하는 창구다** — 품목 수와 로트 수가 같으면
모든 줄의 원가가 상품에 붙은 것이고, 로트가 적으면 그만큼 원가가 떠 있는 상태라 빨간색으로
표시된다. 청구서를 저장했는데 원가가 실제로 연결됐는지를 화면에서 바로 볼 수 있어야 해서 넣었다.

## 발주 진행 단계 (2026-08-18, 두 번 재설계함)

```
1 청구서 수령 → 2 결제완료 → 3 중국배대지 배송중 → 4 중국배대지 도착
```
`PO_STEPS` 배열의 순서 자체가 의미를 가지므로 바꾸지 말 것.

**왜 "작업비 청구 / 쿠팡 출고중 / 쿠팡센터 도착"이 여기 없나** — 사용자가 처음 말한 순서엔
있었지만, 이어진 확인에서 두 가지가 드러나서 뺐다:
- **부분 출고가 실제로 있다**(사용자 확인) — 100개 중 60개만 보내고 40개는 창고에 남길 수 있다.
- **제트 작업비 청구서는 여러 발주를 가로질러 묶인다** — "28일 주문분 + 29일 주문분을 묶어서,
  그중 없는 건 빼고" 출고 요청한 단위로 온다.

즉 그 세 단계는 **발주 단위로는 참도 거짓도 아니다.** 출고 묶음(`inbound_shipments`) 단위로
따로 관리하고, 발주 화면에서는 "얼마나 나갔나"를 수량으로 보여준다.

**재고 수량을 단계에서 파생시키던 로직도 제거했다** — 부분 출고를 지원하는 순간
"발주 전량이 같이 움직인다"는 전제가 깨지기 때문. 단계 변경은 이제 재고를 안 건드리고,
'중국배대지 도착'만 로트에 `arrived_china_at`을 남긴다(리드타임 실측용).

**불량 수량**(`purchase_order_lines.defect_qty`, 019) — 중국 배대지 검수에서 발견된다.
줄별로 입력하면 창고 수량(`qty_china`)에서 빠지고 **개당 원가는 그대로**다
(불량분은 대행사가 예치금으로 환불해주므로 단가가 아니라 수량이 준다).
로트가 아직 없는 줄은 입력칸이 비활성 — 뺄 재고 자체가 없다.
한국 도착 후 발견되는 경우도 드물게 있다고 해서, 그건 나중에 "재고 조정"으로 따로 다룬다.

**원가는 두 축으로 나눠 저장한다**(019) — `unit_purchase_cost_krw`(구매대행분, 발주 시 확정) +
`unit_work_fee_krw`(배대지 작업비, 출고 시 확정) = `unit_cost_krw`(총합, 이익 계산에 씀).
사용자가 "총합으로 더하되 따로도 저장해두면 나중에 볼 때 좋겠다"고 해서 컬럼으로 뺐다 —
"작업비가 원가의 몇 %인가" 같은 걸 SQL로 바로 물어볼 수 있다.

**작업비 청구서가 쿠팡센터 도착 "전"에 온다**(사용자 확인) — 그래서 물건이 팔리기 시작할 땐
이미 원가가 확정돼 있다. 팔린 뒤에 원가가 바뀌는 문제가 구조적으로 없으므로
**소급 재계산 로직을 만들지 말 것**.

**진행 상태는 발주가 아니라 줄(=SKU) 단위다(`lineProgress()`, 2026-08-18 사용자 요청)** —
한 발주 안에서도 어떤 SKU는 이미 쿠팡에 있고 어떤 건 아직 중국에 있을 수 있다
(부분 출고 + 1688에서 일부만 먼저 도착하는 경우). **상태를 저장하지 않고 로트 수량에서
파생시킨다** — 저장된 상태와 실제 수량이 어긋날 일이 원천적으로 없다.
```
로트 없음                     미연결
창고>0, 나머지 0              중국창고
운송중>0만                    쿠팡 출고중
쿠팡>0만                      쿠팡센터
두 곳 이상에 걸쳐 있음         일부 출고
전부 0                        재고 없음(다 팔렸거나 폐기)
```

## 출고 탭 (2026-08-18 신설) — 원가가 확정되는 곳

중국 배대지 창고에 있는 것을 골라 한국(쿠팡센터)으로 보낸다.
**발주가 아니라 SKU 기준으로 모아서 보여준다** — 실무에서 "이 상품 보내주세요"라고 하지
"6월 26일 발주분 보내주세요"라고 하지 않는다(사용자 확인).

**"도착 예정"과 "중국창고"를 가르는 건 그 로트가 속한 발주의 단계다** — `arrived_cn` 전이면
아직 창고에 실물이 없으므로 `qty_china`가 있어도 "도착 예정"으로 분류한다(`lotArrived()`).
출고 만들기 목록에는 **실제로 창고에 있는 것만** 나온다.

**로트를 쪼갠다** — 100개 중 60개만 보내면 그 60개엔 작업비가 붙고 남은 40개는 안 붙어서
한 로트가 두 개의 개당 원가를 갖게 된다. 나가는 만큼을 새 로트로 떼어내고
(`split_from_lot_id`) 거기에만 작업비를 얹는다. 통째로 나가면 분할 없이 그 로트를 옮긴다.

**여러 발주에서 온 같은 SKU는 오래된 것부터 내보낸다**(사용자 확인) — 창고 운영 순서이자
선입선출 원가 계산과도 맞는다. 정렬 기준은 `arrived_china_at`, 없으면 `ordered_at`.
실측 확인: 91개(6/26분 51 + 7/02분 40) 중 60개 출고 → 6/26 로트 통째(원가 2,560→2,860) +
7/02 로트에서 9개 분할(2,600→2,900).

**작업비는 SKU 기본값(`my_skus.work_fee_items`)에서 채우고 줄별로 고칠 수 있다.**
청구서 총액을 넣으면 우리 계산과 대조해서 차액을 보여준다 — 안 맞으면 사용자가 카톡으로
확인한 뒤 개당 작업비를 고치면 된다. **총액을 안 넣어도 저장된다**(청구서 없이 출고하는
경로가 필요하다는 사용자 요청) — 그때는 `invoice_source='none'`으로 남는다.

**도착 처리**를 누르면 그 출고의 로트들이 운송중→쿠팡으로 옮겨지고 `arrived_coupang_at`이
찍힌다. 이 시각이 **선입선출 정렬 기준**이라 반드시 남겨야 한다.

**아직 안 만든 것**: 작업비 청구서 엑셀 자동 인식(지금은 총액 수동 입력).
구매대행은 PDF, 작업비는 엑셀이라 인식기가 따로 필요하다.

## 판매현황에 실제 매입원가 연결 (2026-08-18) — `loadLotCogs()`

발주·출고에서 확정된 로트 원가를 판매에 붙인다. 결과는 **(날짜|옵션ID) 단위 개당 원가 맵**이고,
`buildDailyRow()`와 `renderSales()`가 `calcMargin({ costKrw })`로 넘겨 쓴다.
`costKrw`가 있으면 그걸 쓰고, 없을 때만 예전 방식(소싱 탭에 손으로 넣은 CNY 원가 x 환율)으로
떨어진다 — 두 값을 섞지 않는다.

> 참고: 예전 경로(`loadItemMeta()` → `product_items` → `user_items.cost_cny`)는 소싱 DB를
> 거치는데, 그건 **다른 판매자 상품을 조사한 목록**이라 실제 판매 옵션과 겹칠 이유가 없다
> (위 "옵션ID 서브타이틀" 항목의 같은 함정). 그래서 원가는 사실상 늘 비어 있었다.
> 이제 로트 기반 실제 원가가 그 자리를 채운다.

**미리 계산해 저장하지 않고 볼 때마다 계산한다** — 로트 원가는 출고 때 작업비가 붙으며 한 번
올라간다. 미리 저장하면 그 시점에 과거 이익을 소급 갱신하는 로직이 필요한데, 매번 현재 로트
원가로 계산하면 그게 아예 필요 없다. (`cogs_allocations`(016)는 나중에 느려지면 쓸 자리)

**판매 이력을 전량 읽는다** — 선입선출은 처음부터 순서대로 소진시켜야 맞다. 조회 기간만 읽으면
이미 팔려나간 옛 로트가 남은 것처럼 계산돼 원가가 낮게 나온다.

**반드시 지킬 두 규칙(2026-08-18 검증 중 발견해서 넣음)**
1. **판매일보다 나중에 도착한 로트는 못 쓴다.** 안 막으면 시스템 도입 전 옛 판매가 최근
   매입분을 끌어다 써서, 없던 원가가 생기고 정작 최근 판매는 로트가 모자라게 된다.
2. **개당 원가는 "덮인 수량"이 아니라 그날 판매수량 전체로 나눈다.** 화면이
   (개당원가 x 판매수량)으로 합계를 내기 때문 — 일부만 덮인 날에 덮인 부분의 평균을 넘기면
   없는 원가가 부풀려진다. 이렇게 하면 합계가 항상 실제로 아는 원가와 정확히 같다.
   실측: 8개 팔렸고 6개분만 알 때 개당 2,145원 x 8 = 17,160원 = 실제 아는 원가.

**반품(음수 수량)은 맨 앞 로트로 되돌린다** — 어느 로트에서 나갔는지는 알 수 없으니 근사다.
로켓그로스는 반품의 상품별 귀속이 구조적으로 불가능하다는 기존 결론과 같은 한계.

## 배대지(제트) 작업비 청구서 엑셀 인식 (2026-08-18)

**구매대행 청구서(PDF)와 완전히 다른 문서다** — 어떤 상품이 몇 개인지가 **아예 없고**
작업 항목별 단가·건수·금액과 총액만 있다. 그래서 읽는 건 **검산용 총액뿐**이고,
상품별 배분은 출고 화면의 SKU 작업비가 담당한다(사용자와 확인).

**한 엔드포인트가 PDF와 엑셀을 둘 다 받는다** — 확장자나 content-type이 아니라
**시그니처(매직 바이트)로 가른다**(`%PDF` vs `PK`=ZIP). 카톡으로 받은 파일은 확장자가
바뀌어 있거나 content-type이 엉뚱하게 오는 일이 흔하다. 응답의 `kind`로 갈라 쓴다.
사용자가 "작업비 청구서는 지금은 엑셀인데 나중에 PDF로 올 수도 있다"고 해서 이렇게 했다.

**`parseZetInvoice(rows)`가 아는 구조**(0-based 열): 3=단가, 4=건수, 5=청구금액.
`청구 금액 합계` / `부가세` / `총 금액 합계` 라벨을 공백 제거 후 매칭해서 찾는다.
**빈 칸이 null이 아니라 공백 두 개('  ')나 '-'로 오는 칸이 많아서** 숫자인지부터 확인해야 한다.
항목 행은 "단가·건수·금액이 모두 숫자이고 금액>0"인 것만 고른다(금액 0인 행은 요금표에만
있고 이번에 청구되지 않은 항목).

**항목 합과 "청구 금액 합계"를 대조해서 다르면 경고한다** — 우리가 못 읽은 항목이 있다는 뜻이다.
**비고란의 구매대행 환율("... x 270 일괄적용")도 뽑아서 보여준다** — 계산엔 안 쓰지만
환율이 바뀐 걸 눈치챌 수 있다.

실측 검증(2026-07-31 청구서): 청구금액 178,800 / 부가세 17,880 / 총액 196,680,
항목 2개(입고분류 200x447, 바코드 100x894) 전부 정확, 항목합 불일치 0, 환율 270 추출.

**`invoice_source`로 총액의 출처를 남긴다**(`xlsx` / `manual` / `none`) — 파일에서 읽은
값인지 손으로 넣은 값인지 알아야 나중에 신뢰도를 판단할 수 있다.

**의존성 주의**: `xlsx`(SheetJS) npm 최신은 0.18.5이고 그 이후 버전은 npm에 안 올라온다.
0.18.5엔 프로토타입 오염 관련 권고가 있으나, 이 함수는 **사용자 본인이 올린 청구서만**
서버에서 파싱하고 결과를 프로토타입에 병합하지 않아 실질 위험이 낮다고 보고 채택했다.
불안하면 SheetJS 공식 CDN 버전으로 바꾸거나 xlsx(zip+xml)를 직접 파싱하는 방법이 있다.

## 재고 · 재발주 제안 탭 (2026-08-18 신설)

다품종 소량에서 가장 큰 손실은 적자가 아니라 **품절**이다. 반대로 많이 사두면 재고에
현금이 묶인다. 사용자 방침: "최대한 타이트하되 품절은 안 나도록, 판매 추이 보면서 점증/점감."

**일평균 = 최근 7일 평균 x 0.6 + 최근 28일 평균 x 0.4**
추이를 자동으로 따라간다 — 최근에 잘 팔리면 7일 평균이 올라가 발주량이 늘고 시들해지면 준다.
사용자가 원한 "점증/점감"이 **별도 규칙 없이** 이 가중치 하나에서 나온다. 28일만 쓰면 반응이
느리고, 7일만 쓰면 하루 튄 값에 휘둘린다. 실측: 최근 7일 4개/일 + 28일 평균 2.5개/일 → 3.4
(28일만 썼으면 2.5로 과소평가).

**재주문점 = 일평균 x (리드타임 + 안전일수)** — 쿠팡 재고로 버틸 날이 이보다 짧으면 조치 필요.
**권장 수량 = 일평균 x (리드타임 + 안전 + 보충주기 14일) − 이미 가진 물량**(쿠팡+운송중+중국창고).
파이프라인을 빼야 이중 발주가 안 된다. MOQ보다 작으면 MOQ로 올린다.

**판정이 두 갈래인 게 핵심** — 부족할 때 **중국 창고에 재고가 있으면 "입고요청"**,
없으면 "발주 필요". 창고에 있는 걸 새로 사는 건 돈과 시간을 모두 버리는 짓이다.

**리드타임은 실측을 쓴다** — 발주 요청일 → 그 로트가 쿠팡에 도착한 날의 평균.
SKU에 값을 직접 넣었으면 그게 우선, 없으면 실측, 그것도 없으면 기본 14일.
화면에 "실측"이라고 표시된다. 예측(설정값)과 실측을 나란히 두는 게 이 프로젝트의 방식이다.

**판매 이력이 없는 SKU는 수량을 제안하지 않는다**("데이터 부족") — 근거 없는 숫자를 자신 있게
내미는 것이 아무 말 안 하는 것보다 나쁘다. 판매중지 SKU도 판정에서 뺀다.

기본값은 `STOCK.defaults` 한 곳에 모아뒀다(리드타임 14 / 안전 5일 / 보충주기 14일 /
이력 28일). 나중에 사용자별·SKU별로 튜닝할 때 여기부터 손대면 된다.

## 사이드바 그룹 구조 (2026-08-18)

탭이 10개가 되면서 `소싱 / 상품 / 공급 / 판매` 4그룹으로 묶었다. 사용자가 설계 초기에
정한 최종 구조는 **소싱 / 상품 / 공급 / 판매 / 경영 / 에이전트** 6그룹인데,
경영·에이전트는 아직 페이지가 없어서 **빈 그룹을 미리 만들지 않았다** —
빈 서랍은 정보가 아니라 소음이다. 페이지가 생길 때 그룹을 추가하면 된다.

```
소싱   소싱 · 카테고리 · 수집 대기열 · 즐겨찾기
상품   상품원장
공급   발주 · 재고 · 출고            <- SCM 그룹. 사용자가 "SCM 페이지" 라 부르는 것
판매   판매현황
```

**마크업 구조**: `.nav-group` > `.nav-group-label` + `.nav-item`들. 페이지 전환 로직은
`$$('.nav-item')`를 그대로 쓰므로 **그룹을 추가해도 JS는 안 고쳐도 된다** —
새 탭을 넣을 땐 해당 `.nav-group` 안에 `<button class="nav-item" data-page="...">`를 넣고
`#page-...` 섹션과 네비게이션의 `if (page === '...')` 한 줄만 추가하면 된다.

**접힌 사이드바에선 그룹 라벨을 숨기고 구분선만 남긴다** — 아이콘만 있어도 묶음이 보인다.

**발주 목록의 "결제완료" 버튼은 단계를 두 칸 넘긴다(`poPayCellHtml()`, 2026-08-18 사용자 요청)** —
누르면 `paid_at`을 남기고 상태를 바로 `shipping_cn`(중국배대지 배송중)으로 바꾼다.
결제하면 쿠플러스가 1688에 주문을 넣고 물건이 움직이기 시작하므로 "결제완료"에 머무는 시간이
실무에 사실상 없다. 단계를 건너뛰는 게 아니라 **결제라는 사건이 곧 배송 시작**이라는 뜻이다.
"언제 결제했나"는 `paid_at`에 남으므로 정보를 잃지 않는다. 결제 후에는 그 자리에 결제일이 뜬다.
버튼 클릭은 `stopPropagation()`으로 행 클릭(상세 열기)과 분리한다.

## 입고 탭 (2026-08-18 신설) — 물건의 물리적 상태

발주 상세가 "원가와 SKU 연결"을 맡는다면 **입고는 "실제로 몇 개가 왔고 몇 개가 불량인가"**를 맡는다.
불량 입력은 **여기로 일원화**했다(발주 상세에서 뺐음) — 같은 걸 두 군데서 고칠 수 있으면
반드시 헷갈린다.

**020이 바로잡은 것**: 예전엔 로트를 만들 때 `qty_china = 발주수량`을 그대로 넣었다.
아직 도착도 안 했는데 창고에 있는 것처럼 기록된 셈이라, 출고 화면이 "그 발주가 도착
단계인가"로 우회 판정을 해야 했다(`lotArrived()`, 지금은 삭제). 이제 로트가 **실제 도착
수량을 직접 갖는다**:
```
qty_ordered − qty_arrived = 아직 안 온 수량 (도착 예정)
qty_china                 = 창고에 실제로 있는 수량 (도착 − 불량 − 출고분)
```

**도착은 SKU(로트) 단위다** — 1688에서 일부만 먼저 오는 일이 실제로 있어서 발주 단위로는
표현이 안 된다. 그 발주의 **모든 줄이 다 도착하면** 발주 단계를 자동으로 '중국배대지 도착'으로
올린다(`inbMaybeAdvancePo()`) — 발주 단계는 이제 "전부 왔는가"의 요약일 뿐이다.

**도착 처리는 증분으로 더한다** — 48개 먼저 오고 3개가 나중에 와도 그때 다시 눌러 쌓으면 된다.
실측: 51개 발주 → 48 도착/3 불량(창고 45, 미도착 3) → 나머지 3 도착(도착 51, 창고 48) →
대기 목록에서 사라지고 발주 단계 자동 전진.

**나중에 발견한 불량은 "중국창고 재고" 구역에서 뺀다.** `defect_disposition`으로
**예치금 환불 / 손실 처리**를 고른다(사용자가 둘 다 가능하다고 확인). 실제 예치금 반영은
자금 화면이 생길 때 하고, 지금은 어느 쪽으로 처리하기로 했는지만 남긴다.
**개당 원가는 절대 안 건드린다** — 불량분은 환불받거나 털지, 남은 정상품 원가를 올리지 않는다.

**재고 화면의 파이프라인에 미도착분도 들어간다** — 안 그러면 이미 주문한 걸 또 발주하게 된다.

**입고 화면은 로트만 보여준다 — 그래서 SKU 미연결 줄을 따로 경고한다** — 청구서 줄에 SKU가
안 붙으면 로트가 아예 안 만들어져서 입고·출고·원가 어디에도 안 잡힌다. 화면엔 그냥 "없음"으로
보여서 원인을 알 수 없었다(2026-08-18 사용자가 실제로 겪음). 맨 위 `#inboundOrphan` 경고가
몇 개인지·어떤 상품인지·어디서 고치는지를 알려준다. **파생 데이터만 보여주는 화면은 원본이
없을 때 그 사실을 말해줘야 한다** — "없음"은 "0개"와 "애초에 안 만들어짐"을 구분 못 한다.

## SKU 없는 로트 (2026-08-18, migration 021)

**상품 등록 전에 먼저 발주하는 경우가 있다**(사용자 확인). 그때는 발주 시점에 바코드가 없고,
물건이 중국 창고에 도착한 뒤 쿠팡으로 보내기 전에 상품을 등록하고 바코드를 받아 바코드 작업을 한다.

예전엔 `inventory_lots.sku_id`가 not null이라 **SKU가 붙어야만 로트가 생겼다** — 그래서 이 경우
물건은 실제로 중국에 있는데 시스템엔 존재하지 않았다. 입고도 재고도 안 잡힌다.

**물건의 존재와 상품 등록은 별개 사건이다.** 로트는 발주 시점에 태어나고 SKU는 나중에 붙는다.
```
SKU 없이 되는 것    입고(도착 처리) · 불량 처리 · 중국창고 재고 확인
SKU가 있어야 하는 것 한국 출고 · 판매 원가(선입선출) · 재발주 제안
                    (바코드가 없으면 애초에 쿠팡에 못 보낸다)
```

**청구서를 저장하면 이제 모든 줄에 로트를 만든다**(예전엔 SKU 매칭된 줄만). SKU 미연결 줄은
`sku_id: null`로 생긴다. 나중에 발주 상세에서 SKU를 연결하면 **새로 만들지 않고 기존 로트에
`sku_id`를 채운다** — 새로 만들면 같은 물건이 두 번 잡힌다. (021 이전에 만들어진 발주엔 로트가
아예 없을 수 있어서 생성 경로도 남겨뒀다.)

**입고 화면은 SKU 없는 로트를 청구서 상품명으로 보여준다** — 물건은 실재하므로 입고·불량 관리는
그대로 된다. 바코드 자리엔 "SKU 미정 — 출고 전에 연결 필요"가 뜬다.
**출고 화면은 SKU 없는 물량을 목록에서 빼되 요약에 수량을 표시한다** — 숨기면 "내 물건이 어디
갔지"가 되므로, 왜 안 보이는지를 알려준다.

## 발주 취소 · 예치금 환불 (2026-08-18, migration 022)

10개 SKU를 발주했는데 그중 2개를 **판매자가 못 팔겠다고** 하는 일이 있다(사용자 확인).
입고의 "도착 대기" 행에서 바로 취소한다 — 어차피 "안 온 물건"을 보고 있는 화면이다.

**발주 수량은 줄이지 않는다.** "20개 발주했는데 20개 취소됨"과 "애초에 0개 발주"는 다른
사실이고, 나중에 "이 공급처는 취소가 잦다"를 보려면 원래 발주량이 남아야 한다.
`미도착 = qty_ordered − qty_arrived − qty_cancelled`.

**환불액은 추정만 하고 사람이 고친다** — 사용자 확인: 배송 전 취소면 배송비까지 돌아오지만,
배송 후면 판매자마다 다르다(배송비를 내가 부담하는 경우도 있다). 그래서
**상품가만 / 배송비 포함** 두 값을 참고로 보여주고 입력칸은 열어둔다. 기본값은 전액 —
덜 받으면 줄이는 쪽이 자연스럽다. 배송비 배분분은 `cost_breakdown.cny_shipping_alloc`에
환율을 곱해 되돌려 계산한다.

**예치금 기록은 `status='expected'`로 남는다** — 예치금은 그때그때 들어오므로 아직 실제
입금이 아니다. 나중에 실제 입금과 맞춰본 뒤 `confirmed`로 바꾼다(그 화면은 아직 없음).
`amount_krw`(사람이 인정한 금액)와 `estimated_amount_krw`(시스템 추정)를 나란히 남겨서
"우리 추정이 실제와 얼마나 달랐나"를 나중에 볼 수 있게 했다.

**불량 환불도 같은 방식으로 기록한다** — 중국창고에서 불량을 "예치금 환불"로 처리하면
`reason='defect'`로 expected 기록이 생긴다. "손실 처리"를 고르면 기록을 안 만든다.

**취소는 되돌릴 수 있다** — 전량 취소해도 행이 목록에 남아 있고(안 남기면 되돌릴 방법이 없다)
"취소 되돌리기"를 누르면 취소 수량이 0이 되고 그 로트의 환불 기록이 `void`로 바뀐다.
**기록을 지우지 않고 void로 남기는 이유**: "취소했다가 되돌렸다"도 사실이고, 예치금을 실제
입금과 맞출 때 지워진 기록보다 무효 표시된 기록이 훨씬 추적하기 쉽다.
